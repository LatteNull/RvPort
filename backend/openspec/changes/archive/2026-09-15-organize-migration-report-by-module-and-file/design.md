## Context

当前迁移评估报告将确认后的迁移输入保存到 `report_inputs.input_snapshot`，并生成不可变的 HTML/JSON 制品。该结构能够保留历史事实，但代码类 finding 仍按单条输入平铺展示；当报告包含大量知识库扫描结果时，用户无法先定位问题集中的模块和文件，也无法在同一文件上下文中联合理解 Header、类型、Intrinsic 等相关问题。

本变更跨越报告生成、数据查询、源码版本、构建上下文、对象存储、路径安全和报告渲染。设计必须同时满足历史报告不可变、项目权限隔离、分页性能和源码上下文可审计降级，并保留依赖分析作为全局清单的既有产品边界。

## Goals / Non-Goals

**Goals:**

- 将代码类报告输入稳定组织为“模块 -> 文件 -> 问题类型 -> finding”，并在每一级提供直接下级统计。
- 使用确定性的模块识别降级链，输出识别依据和置信度，且不因多目标归属重复计算 finding。
- 为报告绑定的源码版本提供文件级联合上下文、高亮和结构化省略区间。
- 为模块、文件、类型和 finding 提供支持分页、过滤、排序和项目权限校验的查询 API。
- 让 HTML/JSON 报告采用相同的组织语义，同时保留现有平铺输入接口和历史报告下载能力。
- 继续按软件包/依赖类型/目标匹配状态/一键修复状态组织依赖输入，不将其强行归入代码模块。

**Non-Goals:**

- 不修改前端实现。
- 不重新定义 finding 的确认规则、风险等级或扫描器输出。
- 不引入“修复包”作为新的持久化业务实体，也不自动规划修复顺序。
- 不将已生成历史报告重新组织或覆盖；历史数据仅提供明确的兼容或不可用状态。
- 不把依赖项映射到源码模块，也不改变依赖一键修复逻辑。

## Decisions

### 1. 报告输入快照增加可查询的组织投影

新报告生成时，后端继续保存完整 `input_snapshot`，同时为代码类输入保存结构化投影字段，包括来源类型、归一化风险、模块键/名称/识别依据/置信度、文件键/相对路径、finding 类型、起止行和源码内容哈希。数据库为报告、模块、文件、类型、风险和稳定行号排序建立组合索引。

选择结构化列而不是查询时解析 JSONB，是因为四级分页与聚合会频繁执行，JSONB 字段又来自不同来源 schema；结构化投影可以提供稳定的过滤、排序和索引边界。`input_snapshot` 仍是历史详情的事实来源，投影仅服务组织与查询。

历史 `report_inputs` 不回填推断结果。报告详情返回组织能力版本和 `organizationAvailable`；旧报告继续通过既有平铺接口和原始 HTML/JSON 制品查看，避免用当前算法重写历史事实。

### 2. 模块识别采用确定性降级链

模块解析器按以下顺序确定归属：

1. 构建上下文中明确关联该文件的构建目标。
2. 链接产物、目标依赖图或编译数据库可反推的构建产物。
3. 向上查找最近的构建描述文件，如 `CMakeLists.txt`、`meson.build`、`Makefile` 或 RPM spec。
4. 使用稳定的目录分组。
5. 回退到项目根模块。

解析结果包含 `moduleKey`、`moduleName`、`basis`、`confidence` 和可选 `relatedModuleKeys`。`moduleKey` 基于识别依据与规范化逻辑标识生成，不包含报告 ID 或源码版本 ID，以便跨源码版本比较；源码版本继续由报告本身隔离。

若一个文件属于多个显式目标，解析器将其归入确定性的共享模块，并通过 `relatedModuleKeys` 表达关联目标，finding 只计数一次。相比把同一 finding 复制到多个目标，这能保证聚合总数与报告输入总数一致。

### 3. 层级 API 返回摘要，子级独立分页

新增以下只读 API：

- `GET /api/reports/{reportId}/code-modules`
- `GET /api/reports/{reportId}/code-files?moduleKey=...`
- `GET /api/reports/{reportId}/code-finding-types?moduleKey=...&fileKey=...`
- `GET /api/reports/{reportId}/code-findings?moduleKey=...&fileKey=...&findingType=...`
- `GET /api/reports/{reportId}/code-files/{fileKey}/context`

父级响应不嵌入所有子记录，而是返回前端绘制当前层所需的直接下级统计：模块返回文件数、finding 数、类型数、最高风险、风险分布和类型分布；文件返回 finding 数、类型数、最高风险、风险分布和类型分布；类型返回 finding 数、最高风险、首末行和符号数。

所有列表接口使用统一分页响应，支持白名单过滤和排序。finding 默认按 `lineStart ASC NULLS LAST, lineEnd ASC NULLS LAST, id ASC` 稳定排序。每个入口先由报告反查项目并执行项目访问校验，禁止跨项目读取。

保留 `GET /api/reports/{reportId}/inputs`，用于兼容既有调用和原始证据审计。

### 4. 文件上下文固定绑定报告源码版本并存入对象存储

报告生成时仅为已纳入报告的代码文件生成上下文索引。后端通过报告的 `sourceRevisionId` 和经过路径安全校验的相对路径读取不可变源码，计算内容哈希，并将可展示的 UTF-8 文件内容或行索引作为报告上下文制品保存到对象存储；数据库只保存报告、文件键、源码版本、相对路径、内容哈希、总行数、制品引用和可用性状态，不把大段源码塞入普通字段。

查询上下文时禁止回退读取项目当前 active source revision。这样源码更新后，旧报告的行号、高亮和上下文仍指向生成时内容。对象存储读写失败、文件缺失、二进制文件、超大文件或非法路径不会使整个报告失败，而是记录 `contextAvailable=false`、稳定原因码和可审计摘要。

### 5. 联合上下文使用 CODE/OMITTED 块表达

默认上下文覆盖该文件首个 finding 起始行之前 20 行至最后一个 finding 结束行之后 20 行，并裁剪到文件边界。若跨度超过服务端阈值，则围绕每组 finding 合并重叠窗口，中间区域返回结构化省略块：

```json
{
  "kind": "OMITTED",
  "startLine": 121,
  "endLine": 680,
  "lineCount": 560,
  "reason": "DISTANT_FINDING_GAP",
  "loadable": true
}
```

代码块中的每一行返回真实 `lineNumber`、`text` 和 `highlights`；高亮至少引用 `findingId`，并在来源提供列范围时返回起止列。省略内容永远不伪装成代码行。上下文 API 支持 `fromLine` 与 `lines` 读取指定范围，供前端展开 `loadable=true` 的省略块。

无法定位的 finding 保留在文件/类型列表中并标记 `locationAvailable=false`，不得因此丢弃问题或让报告失败。

### 6. 依赖输入保持全局聚合

`DEPENDENCY_RESULT` 不参与模块/文件层级。报告按照 provider 软件包或待安装软件包聚合，展示依赖类型、目标匹配状态、风险和一键修复状态，并将同一 provider 下的 SO/ELF 作为 evidence 合并，避免重复主条目。

这一选择符合当前依赖集合有限且可通过一键修复处理的产品边界，也避免制造不可靠的“依赖属于哪个源码模块”关系。

### 7. JSON 与 HTML 共用一个报告视图模型

报告生成器先构造版本化视图模型，再分别渲染 JSON 和 HTML。结构依次为执行摘要、代码模块/文件层级、全局依赖迁移列表和原始证据附录。HTML 默认展示聚合摘要，详细 finding 和大段源码使用折叠或分页入口，避免把数万行 DOM 一次性渲染。

共用视图模型可避免 HTML 与 API/JSON 的统计口径漂移。原始 evidence 仍来自不可变输入快照，不从当前分析表重新拼接。

## Risks / Trade-offs

- [构建元数据不完整导致模块识别退化] -> 返回 `basis` 和 `confidence`，使用明确降级链，并保证最终总能落入目录或根模块。
- [共享源码属于多个目标] -> 使用单一共享模块和关联模块列表，避免重复统计，同时保留关联线索。
- [单文件 finding 跨度极大造成响应和页面过重] -> 合并局部窗口并使用结构化 `OMITTED` 块，按需读取具体行范围。
- [报告上下文制品数量增加] -> 仅为纳入报告的代码文件创建制品，复用对象存储生命周期和报告删除策略。
- [历史报告缺少组织投影] -> 不猜测、不回填，显式返回不可用状态并保留平铺接口及既有制品。
- [路径或源码文本泄露] -> 仅接受报告内 opaque `fileKey`，相对路径必须通过安全解析，API 不返回宿主机真实路径或对象存储 key。
- [组织列与 input_snapshot 不一致] -> 在同一报告生成事务中从同一个不可变快照构造投影，并用测试校验各级总数守恒。

## Migration Plan

1. 增加报告输入组织投影和文件上下文元数据的数据结构、索引及 jOOQ 元数据。
2. 实现模块解析器、投影构造器和文件上下文制品生成；新报告写入新的组织 schemaVersion。
3. 增加层级查询与上下文 API，并保留现有平铺接口。
4. 更新 JSON/HTML 渲染器，验证聚合总数与输入快照一致。
5. 运行数据库迁移、单元测试、API E2E、覆盖率门槛和 OpenSpec 严格校验后部署。

回滚时可停止写入和暴露新组织能力，保留新增列/表和对象存储制品；旧平铺 API 与历史报告不受影响，不执行破坏性数据回滚。
