## Why

当前迁移评估报告虽然保存了完整的确认输入，但报告正文和查询接口主要按单条输入平铺展示；当同一项目产生数百至数万条代码 finding 时，用户无法快速判断问题集中在哪些模块和文件，也难以在同一文件上下文中完整处理 Header、类型、Intrinsic 等相互关联的问题。需要把代码类报告输入组织为稳定的“模块 → 文件 → 问题类型 → 具体问题”层级，并提供文件级联合代码上下文，同时保持依赖分析按软件包整体展示。

## What Changes

- 将迁移报告中的代码类输入按模块、文件、问题类型和具体问题四级组织，每一级返回直接下级数量、风险分布和类型分布等统计。
- 为模块识别建立确定性的降级链：显式构建目标、构建产物反推、最近构建描述文件、目录分组、项目根回退，并返回识别依据和置信度。
- 增加报告代码模块、模块文件、文件问题类型和具体 finding 的分页查询能力；具体 finding 默认按起始行、结束行和稳定 ID 升序排列。
- 增加文件级联合代码上下文：从文件内首个纳入报告的 finding 上 20 行展示到最后一个 finding 下 20 行，并高亮该文件内所有纳入报告的 finding。
- 对跨度过大的文件上下文使用结构化 `CODE` 与 `OMITTED` block；省略范围、行数、原因和可加载状态必须作为字段返回，禁止把“省略若干行”伪装成源码文本。
- 文件上下文必须绑定报告的不可变源码版本和输入快照；源码缺失、行号失效、无法定位或超大文件时返回可审计的降级状态，而不是导致报告失败。
- 依赖分析输入继续按软件包、依赖类型、目标匹配状态和一键修复状态整体展示，不强行归入代码模块或文件。
- 调整迁移报告 JSON 与 HTML 结构，形成执行摘要、源码模块/文件层级、依赖迁移列表和原始证据附录；历史报告继续保持不可变和可下载。
- 补充不依赖外部服务的单元测试，以及覆盖正常流程、异常流程和 edge case 的独立 API E2E；项目整体与受影响模块的行覆盖率和分支覆盖率均须达到至少 90%。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `migration-report-runtime`：增加模块/文件/类型/finding 四级组织、逐级统计、模块识别依据、文件联合上下文、结构化省略块和独立依赖展示要求。
- `api-e2e-test-suite`：增加迁移报告层级查询、行号排序、文件上下文高亮、结构化省略、历史源码版本和权限隔离验证。

## Impact

- 影响迁移报告生成服务、报告输入快照、报告详情与输入查询 API、HTML/JSON 制品以及相关 DTO 和仓储查询。
- 可能需要为报告输入补充可查询的组织字段或独立聚合结构，并为模块、文件、类型分组和稳定排序增加数据库索引。
- 需要复用源码版本、构建上下文和路径安全能力，确保模块识别与文件内容读取均限定在报告绑定的源码版本内。
- 前端后续可基于新增 API 懒加载模块、文件、类型和 finding，并使用结构化代码块渲染高亮与省略区域。
- 不改变依赖分析与一键修复的业务边界，也不删除既有平铺输入和历史报告下载能力。
