## Why

依赖分析已经能够识别源环境中使用的软件包、目标环境中可用的软件包及其版本关系，但用户仍需要手动登录目标环境安装可替代依赖。对于源环境和目标环境属于同一类发行版包生态、且目标源已经确认存在可用包的场景，后端可以提供受控的一键修复能力，减少重复人工操作并在修复后自动重新分析。

## What Changes

- 新增依赖自动修复运行时：基于某次依赖分析结果生成可修复候选项，并支持用户提交选中的结果项创建异步修复任务。
- 新增依赖自动修复 API：提供候选项分页查询、创建修复任务、修复运行详情、修复条目列表和项目级修复历史查询。
- 新增依赖自动修复数据表：逐条记录安装计划、安装状态、安装结果、错误摘要和重跑依赖分析关联信息。
- 扩展任务运行时：新增 `DEPENDENCY_AUTO_FIX` 任务类型，复用现有 RabbitMQ worker、任务日志、任务事件和取消机制。
- 修复任务在目标环境安装软件包后，自动刷新环境并重新创建依赖分析任务；如果没有任何实际安装成功，则不强制重跑分析。
- 修复任务必须校验项目权限、依赖分析上下文、当前源码版本、当前运行环境配置版本和包名安全性。
- 扩展 API E2E：覆盖候选项查询、默认选择规则、越权访问、非法条目、安装失败、部分成功、自动重跑依赖分析和数据清理。
- 如果依赖自动修复生成可下载或可归档摘要制品，则必须登记归档候选；没有制品时仅保留任务和运行记录。

## Capabilities

### New Capabilities

- `dependency-auto-fix-runtime`: 定义依赖自动修复候选项、异步安装任务、修复结果记录和修复后自动重跑依赖分析。

### Modified Capabilities

- `dependency-analysis-runtime`: 依赖分析结果需要提供自动修复候选项来源，并约束哪些风险等级和匹配状态可进入自动修复。
- `task-runtime`: 新增 `DEPENDENCY_AUTO_FIX` 任务类型，并要求该任务接入现有任务状态、日志、SSE 和取消机制。
- `api-e2e-test-suite`: 新增依赖自动修复端到端测试，覆盖正常流程、异常流程和 edge case。
- `project-archive-runtime`: 明确后续若依赖自动修复产生报告或摘要制品，必须按全局归档规则登记候选。

## Impact

- 后端 API：新增依赖自动修复候选项、创建、详情、列表接口。
- 数据库：新增 Liquibase 变更和 jOOQ 生成代码；新增修复运行表和修复条目表；更新 `tasks_type_chk`。
- Worker：新增 `DEPENDENCY_AUTO_FIX` handler，复用 SSH 远程执行、任务日志和任务事件。
- 依赖分析：复用现有 `sourceProviderPackage`、`targetProviderPackage`、`providerVersionStatus`、`riskLevel` 和 `targetMatchStatus` 字段，不改动依赖识别主流程。
- 测试：新增单元测试和 API E2E 模块测试；E2E 应在容器中运行，并满足正常流程、异常流程和 edge case 三类覆盖。
