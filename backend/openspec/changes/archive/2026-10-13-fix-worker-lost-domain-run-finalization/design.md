## Context

WorkerCleanupItemService.reconcile 事务内将句柄标为 WORKER_LOST，仅调用 failRunningWorkerLost 更新 Task 并发送事件。各领域 run 由 handler 自行结束，因此失联时不会收尾。DependencyAnalysisRepository.findLatestRun 优先活动记录，ProjectWorkflowStatusService 直接读取 run.status，而领域 latest 的 execution 读取 Task，形成状态分裂。

TaskRepository.complete 仅保护 CANCELLED，markRetry 没有状态条件；依赖分析 markRunning/markFinished 仅按 runId 更新。恢复的旧进程可能覆盖清理结果。现有句柄 ID 可标识一次执行，但不能仅靠 JVM 内标记或写入前单次查询保证并发安全。

本 change 只修改 backend，不修改前端和工具。截图来自外部实例，实施前先查询实际不一致记录，不将截图视为本地数据库证据。

## Goals / Non-Goals

**Goals:**
- 失联终态与关联非终态领域记录一致，latest/overview 不被僵尸记录阻塞。
- 旧执行失去写入资格后不能恢复任务或发布当前业务结果。
- 安全、幂等修复历史非终态记录，保留正常重试和成功历史。

**Non-Goals:**
- 不重写所有业务状态机，不改变风险/部分成功的领域语义。
- 不自动重跑失联任务，不保证物理进程已停止，不新增调度平台。
- 不删除历史日志、报告、制品，不新增公共修复接口。

## Decisions

### 1. 统一收尾服务与显式领域适配器

新增后端内部收尾服务，以 taskId、终态、错误码、安全原因和结束时间调用按任务类型注册的领域适配器。使用真实 taskId 关联，而非按项目最新记录更新。失联清理不调用 handler，不依赖失联进程回调，也不由 overview 查询时偷偷修改数据。

实施先建立任务类型到领域记录的覆盖清单：依赖分析/自动修复、KB/AI 扩展、浮点/内存序、x86/双环境构建、自动化测试/比较、报告、归档、源码获取/部署、环境执行及 tool_runs。存在领域运行记录的类型必须提供适配；没有独立记录的类型显式声明无需领域收尾，不能静默遗漏。按 Task 实际关联收尾，双环境和父子任务不得因为一个子任务失联而覆盖仍独立运行的兄弟任务。

仅更新非终态业务记录；已有成功、部分成功及失败结果保持原样，不强制让所有领域状态与 Task 字符串相同。专项分析映射到自己的 FAILED/CANCELLED/TIMEOUT。保留已有 summary 信息，合并安全错误原因。已完成领域结果与 Task 异常终态的组合记录审计，不在本次自动判定结果作废。

### 2. 事务内同步，事务提交后通知

失联时按固定锁顺序校验 Worker 心跳和当前执行归属，锁定 Task，更新失效句柄、Task、关联非终态 run/tool run、临时 secret 清理及 task.failed 事件。任一数据库步骤失败则整体回滚，下轮重试。外部 Redis/SSE 通知沿既有提交后机制发布，不能因通知失败回滚已提交结果。

领域更新成功后发布既有节点变化通知；不新增前端事件类型。正常重复清理不重复生成终态事件。锁必须短暂，不能持锁执行 SSH、扫描、上传或模型调用。

### 3. 执行尝试隔离与迟到写入保护

复用 runtimeHandleId 作为执行尝试身份。原子认领时建立当前尝试绑定；若现有表不能可靠区分当前尝试，则通过 Liquibase 增加 tasks 当前尝试引用及必要索引，不按时间或最近句柄猜测。历史无绑定任务仅允许系统对账路径处理，不能放行迟到 worker。

业务写入在短事务中锁定 Task，检查状态为 RUNNING、当前尝试匹配且句柄未失效，再写入领域状态、结果条目、当前引用、迁移输入、归档候选和后续任务。失联收尾竞争同一 Task 锁：成功发布先提交则保留已完成领域结果；失联先提交则拒绝旧发布。仅增加 Task.complete 的条件不能保护先于它发生的业务写入，因此领域发布入口也必须应用同一检查。

进度、重试、完成、句柄终止也须条件更新，并以“实际发生状态迁移”的结果决定是否发事件。日志不得在已发最终游标后继续接受失效尝试的普通任务日志；迟到信息可写服务端脱敏诊断。对象存储上传允许先在事务外准备，提交时失效则不得登记为有效制品，按既有临时文件/孤立对象策略处置，不能删除他人制品。

正常重试只由当前 RUNNING 尝试进入 QUEUED，撤销旧尝试写资格，后续认领建立新身份。已有 handler 的单次失败状态不能直接视作最终失败；按各领域现有重试契约允许新有效尝试启动，但旧尝试不能重开记录。失联 FAILED 不进入自动重试。用户重新运行创建新 Task。

### 4. 独立于 Worker 保留期的历史对账

复用清理调度增加独立有界对账步骤，在 Worker 已删除、句柄已失效时仍扫描到 Task 为 FAILED/CANCELLED/TIMEOUT、领域记录为非终态的组合。默认沿用 cleanup 开关、周期和 batchSize，使用稳定游标或可重复过滤，避免坏记录永久占据批次。每项独立短事务、重新校验状态，并输出脱敏计数和失败原因。

映射 Task 终态、原错误码和 finishedAt；缺少 finishedAt 时记录修复时间及修复来源，不伪造过去时间。保留已终态记录、已有 findings 和制品。Task 为 SUCCEEDED 但 run 非终态不能凭空生成成功结果，记录异常待人工审计，不自动标记成功。已存在 task.failed 不补发重复事件，仅在实际修复领域状态后发既有节点变化通知。无需人工 SQL，也不在 Liquibase 中执行大批业务数据重写。

### 5. 质量与验收

独立单测 mock 数据库/消息/外部连接返回值，覆盖正常、边界、异常及条件写入失败。Linux Docker 全量单测和覆盖率：全部自有可执行源码含未加载源码，整体与受影响模块行及支持的分支至少 90%；列明生成代码/第三方排除，不通过排除业务代码达标。历史缺口超范围时报告并等待扩大范围，不标记通过。

另用容器化 PostgreSQL/API/Worker 验证并发事务、Worker 失联、旧 worker 恢复和历史对账；这不替代单测。不停止用户真实工作任务，使用隔离 fixture/test-support 验证 latest、overview、readiness、SSE、数据库状态及不重复发布。无相关环境时明确未验证，不归档。

## Risks / Trade-offs

- 跨领域改动面较大：先提交覆盖清单，再逐项接入公共事务检查，测试每个适配器。
- 正常重试与最终终态混淆：以 Task 和当前尝试为控制事实，保留领域部分成功语义并增加重试回归。
- 远端进程仍可能运行：只保证不再接受其业务写入，沿既有取消能力尽力清理，不宣称远程副作用回滚。
- 混合版本 Worker 绕过检查：上线期间暂停领取并排空或停止旧 Worker，全部更新后恢复消费。

## Migration Plan

先完成类型清单、单测与事务集成验证；如需 schema 变更用 Liquibase 并更新 jOOQ。上线前保存不一致统计，部署新版 API/Worker，再启用有界历史对账，核对修复计数与接口。

回滚前关闭对账调度并排空 Worker；已修复终态不恢复为 RUNNING，保留兼容性新增列。旧版本仍有缺陷，不能通过回滚恢复失效任务执行资格。

## Open Questions

无产品阻塞项。实施需确认任务类型覆盖清单及现有 runtime handle 是否支持可靠的当前尝试绑定；不能以省略迟到写入保护替代该核验。
