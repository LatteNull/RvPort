## Context

报告运行时已经能够在当前源码版本没有 `CONFIRMED` 迁移输入时生成成功的空报告，但 `StageReadinessService` 仍把报告阶段的 `INCLUDED_FINDINGS` 计算为 `MISSING`，报告创建入口又复用该前置条件，因此运行时能力与阶段门禁互相矛盾。

任务日志通过追加写入形成物理文件，文件头是最早日志、文件尾是最新日志。当前 `TaskLogTailReader` 从文件头按 offset 读取，相关规格和测试也错误模拟了“最新日志在文件头”，前端随后对页和页内行同时反转，最终使自动化测试等完成态日志倒序展示。运行中的 `/log-increments` 按事件 ID 正序读取，不存在同一问题。

## Goals / Non-Goals

**Goals:**

- 让项目级报告阶段 readiness、报告页 readiness 和报告实际生成行为一致，允许零确认输入生成全零报告。
- 保持 `INCLUDED_FINDINGS` 前置条件字段稳定，并返回真实输入数量供前端展示。
- 恢复完成态日志“最新页优先分页、页内时间正序”的契约。
- 保持现有 API 路径、查询参数、响应字段和日志文件格式兼容。
- 通过正常、异常和边界测试覆盖修正后的契约，并验证受影响模块及项目整体覆盖率至少 90%。

**Non-Goals:**

- 不改变报告内容、报告制品格式、迁移输入确认规则或源码版本前置条件。
- 不修改日志写入方向，不重写既有日志文件。
- 不改变任务级 SSE、项目级 SSE 或 `/log-increments` 的事件游标与增量顺序。
- 不引入数据库迁移或新的 API。

## Decisions

### 1. 零确认输入时将 `INCLUDED_FINDINGS` 视为已满足

当项目存在有效源码版本时，报告阶段的 `INCLUDED_FINDINGS` 始终返回 `SATISFIED`，`details.count` 仍返回当前有效 `CONFIRMED` 输入数量，包括 0。缺少有效源码版本时继续返回 `MISSING` 和稳定的源码缺失原因码。

选择保留该 prerequisite 而不是删除字段，是为了维持 readiness 响应结构兼容，并让前端继续展示输入事实。另一种方案是在报告创建入口绕过 readiness 校验，但会保留查询结果与写接口行为不一致的问题，因此不采用。

### 2. 以追加写入的物理日志为唯一顺序事实

日志文件定义为按产生时间追加：文件头最旧、文件尾最新。`offset=0` 从文件尾读取最后 `lines` 个逻辑行；`offset=N` 跳过最新的 N 行，再读取其前方最多 `lines` 行。返回页中的 `content` 始终按文件自然顺序排列，即页内从旧到新。

例如文件包含 1 到 300 行：

```text
offset=0,   lines=100 -> 201..300
offset=100, lines=100 -> 101..200
offset=200, lines=100 ->   1..100
```

`hasMore` 表示当前页之前是否仍有更早日志。`totalLines`、`returnedLines` 及各日志类型独立 offset 的现有含义保持不变。

### 3. 后端负责页内顺序，前端只负责分页拼接

前端加载更旧页时将该页整体插入已有内容之前，不再对每页的行执行 `reverse()`。这使每个 API 响应可以单独阅读，也避免单页内部时间倒序。运行中增量日志继续按服务端事件顺序追加，不复用完成态分页拼接逻辑。

### 4. 尾部读取必须避免按页扫描完整文件

日志读取器从文件尾部按块定位换行符，只解码请求窗口需要的字节范围；不得为了读取最后 100 行而逐行扫描整个大型日志。实现需要兼容 `LF`、`CRLF`、末尾无换行、空文件、超长单行和 offset 超过总行数。

采用尾部块读取而不是将整个文件载入内存，可以把常见首屏读取的 I/O 和内存消耗限制在日志尾部附近。若现有 `totalLines` 元数据可用，可用于分页事实，但正文窗口仍以日志文件快照为准，避免运行中追加造成越界。

### 5. 测试以真实物理顺序表达契约

后端读取器测试使用 `oldest ... newest` 的写入顺序，覆盖首屏、向前翻页、分页边界、缺失文件、不同换行、无尾换行、超长行和大文件。readiness 测试覆盖有输入、零输入、无源码版本以及报告创建入口的校验一致性。API/E2E 契约测试覆盖多页、单页和空页，并向前端明确页内不得反转，防止再次引入顺序偏差。

## Risks / Trade-offs

- [风险] 尾部块读取容易在 CRLF、UTF-8 多字节字符或文件末尾换行处产生边界错误。 -> 使用字节边界定位完整行窗口后统一 UTF-8 解码，并以多种换行和中文日志用例验证。
- [风险] 日志仍在追加时，文件正文与数据库 `totalLines` 可能短暂不一致。 -> 每次请求使用一次文件大小快照读取正文，并保持 `totalLines` 为响应时刻的近实时统计；完成态任务不存在持续追加竞争。
- [风险] 后端与前端只修改一侧会继续出现顺序错误。 -> 在同一变更中更新双方测试，并用跨两页的时间序列做 E2E 验证。
- [取舍] 零输入报告不再通过 readiness 提醒“没有发现项”。 -> 仍通过输入数量 0 和全零报告表达事实，不把“没有问题”误判为流程错误。

## Migration Plan

1. 修正 readiness 计算和报告创建相关测试。
2. 修正尾部读取器和服务测试，并明确前端分页拼接契约；前端代码由其独立变更适配。
3. 更新主 API 文档中的冲突描述。
4. 运行后端和前端单元测试、覆盖率检查，再使用已完成的多页自动化测试日志验证首屏与向前翻页。
5. 部署无需数据库迁移；若需回滚，可整体回滚应用版本，既有日志文件无需转换。
