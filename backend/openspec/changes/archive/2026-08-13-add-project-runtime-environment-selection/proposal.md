## Why

当前 SBOM、源码部署、构建验证和自动化测试在不同入口选择或携带环境，容易出现 SBOM 分析环境与构建/测试环境不一致，导致报告结论和实际运行结果不可比。需要将远程运行环境选择前置到环境管理中，作为项目级运行环境事实来源。

## What Changes

- 新增项目级运行环境配置，保存当前源环境和目标环境。
- 运行环境配置必须同时具备源环境和目标环境后，才能执行 SBOM、源码部署、构建验证、自动化测试等依赖远程环境的节点。
- 环境设置接口允许一次只设置源环境或目标环境，也允许同时设置两者；但运行节点必须校验双环境完整。
- SBOM 分析、源码部署、构建验证和自动化测试不再让前端传环境选择字段，而是由后端读取项目当前运行环境配置。
- 环境配置变更后，环境相关结果按版本判定为非当前结果；后续相关节点需要重新运行。
- 源码更新不影响环境检查和环境快照本身，但会使源码相关分析、构建、测试和报告需要按新源码版本重新运行。

## Capabilities

### New Capabilities
- `project-runtime-environment-selection`: 项目级双环境选择、版本化和运行前置校验。

### Modified Capabilities
- `backend-api-design`: SBOM、源码部署、构建验证、自动化测试 API 不再由前端提交运行环境选择，改为读取项目运行环境配置。
- `backend-database-design`: 新增项目运行环境配置表和运行记录环境配置版本字段。
- `project-source-environment`: 环境管理负责设置项目当前运行环境，并表达环境变更对后续节点有效性的影响。
- `sbom-analysis-runtime`: SBOM 创建从项目运行环境配置读取双环境，并保存环境配置版本。
- `source-deploy-runtime`: 源码部署从项目运行环境配置读取双环境，不再由请求传环境列表。
- `build-validation-runtime`: 构建验证从项目运行环境配置和源码部署结果创建构建，不再由请求传源码部署环境选择。
- `automated-test-runtime`: 自动化测试从构建结果或项目运行环境配置确定环境，不再由请求传 `environmentId`。

## Impact

- 新增 Liquibase changelog、jOOQ 生成源码和 repository/service。
- 修改环境管理 API、项目 overview、SBOM 创建、源码部署创建、构建创建和测试创建请求/校验逻辑。
- 需要更新独立 E2E 用例，验证缺少双环境时运行节点失败，设置双环境后节点使用一致环境。
- 旧 API 字段需要兼容策略或明确废弃错误，避免前端迁移期间误用。
