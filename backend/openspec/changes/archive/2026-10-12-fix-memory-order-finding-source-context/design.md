## Context

后端 finding() 已为两类专项分析共用 readCodeContext()，按已入库 filePath/startLine/endLine 读取版本工作副本；工具也已有 source_projection()、源码快照和上下文预算。缺口主要位于工具投影：正式 publication/advanced-atomic 及 discharged 调用未传 location；源码候选用 AST 行号却固定使用主翻译单元文件。缺少位置时后端正确返回不可用原因，但不能自行猜测证据位置。

本地数据库当前没有 MEMORY_ORDER Finding，不能把静态发现当作用户记录的完整诊断。实施先保留可复现实例，再对比工具 JSON、落库 detail 和详情响应。默认实施根为 backend；tools/memory-order-analyzer 需要特别范围授权，其他工具和前端不修改。

## Goals / Non-Goals

**Goals:**
- 从真实证据恢复主位置及关联位置，返回可信代码、行号和高亮。
- 正式风险、源码候选、已消解审计结果使用一致的位置解析语义。
- 保留现有详情 API、版本绑定、权限、状态和有限预算。

**Non-Goals:**
- 不增加独立取代码 API，不给列表中的全部记录展开源码。
- 不修改内存序规则、风险等级、BC 构建或并发证明算法；不把候选升级为正式风险。
- 不回填历史扫描，不修复前端，不执行用户源码，不改变报告登记机制。

## Decisions

### 1. 在工具中解析证据位置，后端只适配

以 assessment 引用的 access/event/node/relation 和现有 provenance 建立受 scope、物理 TU、编译上下文约束的查找，追到真实 AST 源码位置或带调试信息的 IR 位置。复用现有索引；不按符号名全局猜测、不默认首个 TU、不把模块路径当源码路径。

沿现有 primaryLocation、occurrences、evidenceChain.steps.source 输出位置，避免另造协议。关联多个访问时完整保留有界可信位置；优先使用结论显式关联的主访问，否则在已确认关联的位置中按角色、相对路径和坐标稳定排序选主位置。步骤只挂接属于自身的证据，不把主位置复制到所有步骤。没有可验证关联则保持 null 并输出双语原因与稳定原因码。

不在 Java 重建工具内语义图，因为 Java 不拥有线程、访问和对象的证据解析职责。

### 2. 文件归属、宏位置与源码快照必须一致

解析 point 自身的文件而非主 TU 文件。仅对已声明源码根下的可信项目文件创建或复用内容哈希快照，校验路径及摘要。头文件也按实际文件取快照；项目外文件不得随意读取或打包。

宏的 expansion 和 spelling 均有有效位置时优先使用可追溯的项目内 expansion 作为展示主位置，保留不同的可信 spelling 位置及来源角色；只有 spelling 可用时显式采用 spelling。缺失或冲突不能拼接成一个假范围。跨文件 start/end 不能当作单文件范围，降级为可信单点或明确不可用。同文件范围采用工具既有 end-exclusive 语义，后端行高亮正确处理 end.column=1 的下一行边界。

上下文默认前后各 20 行，沿用工具 maxLines/maxCharacters 和后端文件大小限制；超限结构化标记截断，缺文件、摘要不一致、越界和非 UTF-8 均保留明确原因，不能硬填其他文件内容。

### 3. 保持详情一次返回及历史语义

后端继续导入主位置到关系字段，完整保存工具 detail；现有 GET memory-order-findings/{findingId} 返回 codeContext/codeContextUnavailableReason，不新增路由。主位置代码取 Finding 绑定的 sourceRevision；逐位置/步骤的嵌入上下文保持工具的可信快照内容。权限、路径防逃逸和不存在资源处理沿用公共能力。

实施需核对版本工作副本与工具 sourceSha256：有摘要时不返回摘要不符的当前文件片段，明确不可用原因；不引入任意文件读取或临时绕过安全校验。历史无摘要/无位置记录按既有行为读取，不静默重写或猜测。

展示内容不进入既有 Finding 语义身份种子；因真实位置被纠正而变化的 occurrence 身份及新语义摘要按既有契约重算。验证重复输出确定性，不承诺所有旧错误位置派生 ID 不变。使用既有结果/审计制品及归档登记，无新报告类型。

### 4. 单测、端到端及文档验收

独立单测覆盖正常、异常、边界，mock 外部连接返回值。Linux Docker 运行后端与工具全量单测及覆盖率门禁：全部自有可执行源码含未加载模块，整体和受影响模块行/可用分支均至少 90%；第三方、生成文件排除项明确说明，不能排除业务模块凑数。历史缺口超范围时报告差距，不标记完成。

真实 Clang 验证主文件、头文件、宏、AST-only 和 AST+BC；通过正式 API 创建至少一条有源码候选的扫描，并验证可重现的正式风险路径。若用户实例不可用，保留独立 fixture 的原始输入输出和 API 审计，不宣称复现用户实例。对照 JSON、DB、详情的路径/行号/文本/高亮及状态，未知位置必须有负例。

工具规范同步 memory-order-finding-evidence-projection、必要时 unified-project-analysis-entry，中文说明落到工具 doc；后端更新 docs/specialized-finding-code-context.md。工具对外新说明同时提供中文/英文，使用其既有字段命名约定。

## Risks / Trade-offs

- 上游评估没有充分的引用链：保持不可用并记录断点，不通过排序掩盖身份歧义。
- 一条风险涉及多线程多文件：主片段只能作为入口，保留逐位置与步骤关联，不把一个片段当全部证据。
- 快照数量增大：按路径/内容复用，继续执行既有预算，显式记录不完整性。
- 后端公共上下文边界修正可能影响浮点：增加两类分析回归，不扩大浮点规则修改范围。

## Migration Plan

先固定回归样本，修复工具及后端最小适配，完成门禁和规范同步，再构建包含新工具的 API/worker 镜像并真实验证。新扫描使用修复逻辑，历史制品不重写；回滚镜像不需数据库迁移。只有所有验收通过才归档。

## Open Questions

- 用户已在 apply 时授权 tools/memory-order-analyzer 特别允许范围。
- 用户实际 Finding ID/JSON 尚未提供；实施时确认是否在目标实例可取，无法取得则明确验证范围。

## 实施补充

真实 API fixture 复现了第二处映射断点：后端 bundle 的主源码副本被重命名，但 AST 仍指向
原项目工作副本。适配器现通过既有 profile.path_map 显式声明本地/远端源码根到项目相对路径
的映射。工具从唯一且含已验证主源码的本地根建立头文件快照，不通过文件名后缀猜测。
远端根仅用于调试位置映射，不能用于任意本地文件读取。头文件预算为单文件 8 MiB、累计
64 MiB；没有直接源码依据的分析层不复制主位置。Clang 的零宽单点转为单字符范围，
倒置范围继续拒绝。工具缓存 source_projection_revision 更新为 2，原 schema 保持不变。
