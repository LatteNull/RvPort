## Why

当前环境检查只保存任务日志和连接状态，不会生成可供 API 展示的 OS、内核、架构、包管理器和基础工具信息；而独立的“环境采集信息”入口后续会从普通前端流程中移除。为了让环境检查完成后即可形成稳定的环境摘要，后端需要把轻量环境信息采集合并进环境检查。

## What Changes

- 环境检查成功时同时采集并保存轻量环境摘要，包括 OS、版本、内核、架构、包管理器、基础工具、工作目录和权限检查结果。
- 环境检查成功后写入或更新可查询的环境基础快照，并更新环境最近检查/采集相关状态，供后端 API 返回。
- 环境检查失败时不得覆盖上一轮成功的环境摘要或快照，只更新失败任务、日志和连接状态。
- 保留重型 `ENV_COLLECT` 能力供 SBOM 分析等后端流程使用，但不再把普通环境信息展示依赖到单独采集入口。
- 环境列表、详情和快照相关 API 需要能返回环境检查产生的基础信息，方便前端展示；本 change 不实现前端页面改造。
- 后端测试覆盖正常流程、异常流程和 edge case。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `project-source-environment`: 环境检查语义从单纯检查扩展为检查加轻量基础信息采集，并明确与重型环境采集的边界。
- `backend-api-design`: 环境相关 API 需要暴露环境检查产生的基础信息和任务/快照查询行为。

## Impact

- 后端运行时：`SshRuntimeService` 环境检查命令、解析、写入快照/摘要逻辑。
- 后端 API：环境列表、详情、快照或任务详情中的环境基础信息返回。
- 数据库：优先复用现有 `environment_snapshots` / `environment_components` / `environments.last_collected_at`；如字段不足，再补充轻量、兼容的迁移。
- 测试：补充环境检查成功写入基础信息、失败不覆盖旧数据、权限隔离和日志保存相关测试。
- 前端：仅作为接口消费方，不纳入本 change 实现范围。
