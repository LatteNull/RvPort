## Why

项目创建时已经移除了 C/C++ 代码来源字段，但源码管理仍需要在首次成功入库后固定项目源码来源，避免同一项目混用压缩包上传和 Git 同步导致后续流程无法判断源码来源语义。当前压缩包上传只保存文件并创建源码版本，尚未自动解包到后端运行目录，也没有把解包目录作为源码工作副本保存。

## What Changes

- 在项目持久化模型中增加项目级源码来源锁定字段，用于记录首次成功源码入库方式：`ARCHIVE` 或 `GIT`。
- 上传源码压缩包成功并解包成功后，将项目源码来源锁定为 `ARCHIVE`；Git 同步成功后，将项目源码来源锁定为 `GIT`。
- 后续源码入库请求必须与项目锁定来源一致；不一致时返回明确业务错误，不创建源码版本、不创建导入成功记录、不投递任务。
- 压缩包上传后由后端自动解包到独立源码运行目录，并将 `source_revisions.working_copy_path` 写入解包目录。
- 支持源码包格式：`zip`、`rar`、`7z`、`tar.gz`、`tgz`、`tar.xz`、`gzip`；`gzip` 作为单文件压缩格式处理，解压后必须满足源码结构校验。
- 解包过程必须防路径逃逸、限制无效源码结构，并保证 API 响应和事件不暴露服务器真实路径。
- 保持前端上传进度由前端控制；后端只负责上传接收、格式校验、解包、持久化和最终成功/失败响应。

## Capabilities

### New Capabilities

- 无。

### Modified Capabilities

- `project-source-environment`: 项目源码管理增加项目级源码来源锁定、压缩包自动解包和源码工作副本路径持久化要求。
- `backend-database-design`: 项目表增加源码来源锁定字段，并约束取值和索引/查询边界。
- `backend-api-design`: 项目和源码 API 响应、错误语义和上传源码包行为需要体现源码来源锁定与解包结果。

## Impact

- 数据库：新增 Liquibase 迁移更新 `projects` 表，重新生成 jOOQ 代码。
- 后端源码管理：更新 `SourceService`、`SourceRepository`、DTO、压缩包处理工具和相关校验。
- API：项目详情/列表/概览返回源码来源锁定字段；源码上传/Git 同步增加锁定校验和明确错误码。
- 依赖：可能需要引入可处理 `rar`、`7z`、`tar.*`、`gzip` 的归档解析库，优先选择 Java 后端可维护且许可证可接受的实现。
- 测试：补充正常流程、异常流程和 edge case 单元测试/E2E 模块测试。
