## Context

迁移输入已经从独立合并节点转为各分析节点内确认。依赖分析、知识库扫描等节点在完成后会把结果同步到 `migration_input_refs`，评估报告再读取当前源码版本下 `CONFIRMED` 的迁移输入生成报告。

当前同步逻辑是追加式：新分析结果会插入迁移输入，但同一源码版本下上一轮分析产生、这一轮已经不存在的旧输入不会被清理。对于同一源码版本和环境版本内的重跑，产品语义应当是刷新当前分析结果，而不是保留多轮历史输入。

## Goals / Non-Goals

**Goals:**

- 节点成功重跑后，当前源码版本下同一来源类型的迁移输入与本次最新结果保持一致。
- 防止旧依赖分析结果、旧 KB finding 等已经不存在的项继续以 `CONFIRMED` 状态进入新报告。
- 保持历史报告快照不可变，已生成报告仍可按当时输入复现。
- 保持现有风险默认策略：低风险默认候选，其他等级默认确认。

**Non-Goals:**

- 不新增 `STALE` 状态。
- 不做跨源码版本的迁移输入继承。
- 不尝试保留同一源码版本内旧输入的人工确认状态。
- 不修改前端 API 路径和报告下载格式。

## Decisions

### 使用替换式同步而不是追加式同步

节点成功完成后，以 `project_id + source_revision_id + source_type` 作为同步范围，先清空该范围下旧迁移输入，再按本次最新结果重新插入。

这样可以保证同一版本内的报告始终基于最新节点结果，避免旧错误项污染报告。代价是重跑会丢弃用户对旧结果的人工确认状态，但这符合“重跑即刷新当前版本”的语义。

### 只在节点成功后刷新迁移输入

如果节点运行失败或取消，不应清空旧迁移输入。否则一次失败的重跑会让当前报告输入突然消失，影响用户继续查看和生成报告。

依赖分析等节点应在结果落库成功后再刷新迁移输入。刷新迁移输入失败时，节点应失败或至少明确记录错误，避免分析结果和迁移输入不一致。

### 历史报告快照不回写

`report_inputs` 是报告生成时的输入快照，代表历史事实。当前迁移输入刷新不应修改历史报告；用户查看旧报告时仍应看到当时纳入报告的内容。

### 空确认输入生成完美报告

如果当前源码版本下没有任何 `CONFIRMED` 迁移输入，报告生成不应失败。该状态表示当前没有需要纳入评估报告的问题，系统应生成一份成功的空输入报告，摘要中的各类问题数量、高风险数量和预计工作量均为 0，总体风险为 `INFO`。

这种语义可以覆盖用户手动撤回所有输入、低风险项默认未纳入报告、或当前节点分析没有发现需处理问题的情况。只有缺少源码版本、任务输入非法、报告记录不存在、制品保存失败等运行错误才应导致报告任务失败。

### 同步范围必须按来源类型隔离

依赖分析重跑只刷新 `DEPENDENCY_RESULT` 来源的迁移输入，不影响 `KB_FINDING`。KB 扫描重跑同理。这样可以避免一个节点重跑误删其他节点的确认项。

## Risks / Trade-offs

- 用户在同一源码版本下手工修改过输入状态，重跑后状态会被重置。→ 接受该行为，节点重跑定义为当前版本结果刷新；需要保留历史时应依赖历史报告快照。
- 如果节点结果落库成功但迁移输入刷新失败，会出现数据不一致。→ 同步逻辑应在同一事务边界或明确失败任务，避免静默成功。
- 如果未来需要保留人工确认状态，需要引入稳定指纹匹配和状态继承。→ 当前不做，避免复杂度提前扩散。
