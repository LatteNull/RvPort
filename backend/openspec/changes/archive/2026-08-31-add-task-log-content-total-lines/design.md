## 背景

`GET /api/tasks/{taskId}/log-content` 当前按 `merged`、`stdout`、`stderr` 三类返回分页日志内容。现有响应包含请求 offset、请求行数、实际返回行数、`hasMore` 和正文内容，但没有暴露每类日志的总行数。

前端需要总行数来展示行号、计算分页状态和滚动状态。日志在任务运行中会持续追加，因此总行数需要随着日志写入或落库增量维护，而不是只在任务完成后计算。

## 目标 / 非目标

**目标：**

- 每个被请求的日志类型都返回 `totalLines`。
- 运行中任务和已完成任务都能返回当前可见的日志总行数。
- 避免每次 `log-content` 请求都扫描大日志文件。
- 保持现有 offset 和 lines 请求语义不变。
- 按正常流程、异常流程和 edge case 补齐测试。

**非目标：**

- 不改变 SSE 动态日志推送语义。
- 不改变日志文件当前的物理存储顺序。
- 不暴露服务器日志文件路径或原始文件系统细节。
- 不引入日志搜索或全文索引能力。

## 设计决策

### 在日志写入时维护行数

任务日志持久化层应在日志内容追加或落库时维护每个日志流的总逻辑行数。该行数可以存储在任务日志元数据行中，也可以使用等效的持久化状态维护。

备选方案是在 `TaskLogTailReader` 每次请求时直接统计文件行数。这个方案实现简单，但面对较大的构建日志和测试日志时会重复扫描文件，成本会随前端翻页和刷新次数放大。

### 每个日志类型独立返回总行数

`totalLines` 应放在每个 `logs.<type>` 对象内部，因为 `merged`、`stdout`、`stderr` 是独立日志流，文件和行数都可能不同。

响应结构保持现有字段兼容，只追加 `totalLines`：

```json
{
  "logs": {
    "merged": {
      "type": "merged",
      "logId": "...",
      "offset": 0,
      "lines": 100,
      "returnedLines": 100,
      "totalLines": 23841,
      "hasMore": true,
      "content": "..."
    }
  }
}
```

### 为旧数据或缺失元数据提供降级路径

如果某条日志记录还没有持久化行数，服务层可以在本次响应中执行一次文件行数统计，或者返回基于当前分页结果的保守值。优先实现仍应是在日志写入路径中维护行数，并在必要时进行回填。

### 保持 offset 语义不变

现有 API 已定义 `offset=0` 表示最新展示页，更大的 offset 表示更旧页面。`totalLines` 描述的是同一个展示方向下的日志流总逻辑行数，不受物理文件是正序还是倒序存储影响。

## 风险 / 取舍

- [风险] 旧日志记录可能没有行数元数据。-> 提供 fallback 统计或回填逻辑，缺失日志文件时返回 `totalLines=0`。
- [风险] 并发写日志时，前端两次请求拿到的 `totalLines` 可能变化。-> 将 `totalLines` 定义为响应时刻的快照，前端按动态增长处理。
- [风险] 没有尾随换行的内容可能被错误少算一行。-> 行数统计必须和日志读取器的逻辑行定义保持一致。
- [风险] 每次小块写入都更新数据库可能增加写入压力。-> 尽量复用现有日志持久化路径，如果已有缓冲机制则按缓冲批次更新。
