## Context

项目详情的画布已有 `build → test` 连线和“自动化测试”节点，但该节点当前被列入延后实现集合，Stage Drawer 也没有对应内容。构建阶段已要求当前源码分别在源端 x86 和目标 RISC-V 环境成功构建。

后端已有可复用的自动化测试能力：`POST /projects/{projectId}/tests` 接收一个成功构建记录与测试命令；运行环境由该构建记录派生，显式提交 `environmentId` 会被拒绝。两个请求使用同一 `testBatchId`，并分别携带 `SOURCE`、`TARGET` 角色时，两个测试结束后服务端会自动创建测试比较记录。任务日志沿用通用 task-log 接口。

## Goals / Non-Goals

**Goals:**

- 让自动化测试成为构建后的可执行节点，并以一套共享配置发起 x86/RISC-V 成对测试。
- 避免用户选择已废弃的环境参数或与当前源码无关的构建记录。
- 在同一个 Drawer 内清晰呈现测试前置条件、两侧运行状态、结果比较和历史；日志使用现有二级 Drawer 模式。
- 复用既有后端接口，不引入新的服务端模型或 API。

**Non-Goals:**

- 本次不落地原型中同组的 Benchmark、性能剖析或 RVV 测试节点。
- 本次不配置或实现手动结果比较、单独重跑失败用例、报告目标上传，或测试用例级详情。
- 本次不改变构建、源码部署或环境检查的业务规则。

## Decisions

### 1. 以“当前源码的最新可用构建对”作为唯一测试输入

Drawer 将从项目构建历史中解析同一当前源码修订的 x86 与 RISC-V 成功构建，并确认两者仍对应当前环境配置。用户只看到每侧选中的构建状态、构建目录和缺失原因，不能手工选择环境 ID 或任意构建记录。

这样可以让测试与当前源码、当前构建产物保持一致，也符合后端“环境由 buildRunId 决定”的契约。备选方案是让用户从构建历史下拉选择；它会带来跨修订、过期环境和 API 废弃参数的风险，因此不采用。

### 2. 一套共享命令，两个派生工作目录

用户配置的测试命令、超时和环境变量对两个测试完全一致。每一侧请求使用其选中构建记录的构建目录作为工作目录；该目录只展示，不在测试 Drawer 中编辑。

构建目录天然是环境相关路径，若把它设计为一项共享可编辑输入会导致至少一侧路径错误。若需要改变目录，用户先回到构建配置重新产生对应构建，而不是在测试阶段修改环境配置。

### 3. 前端创建一个成对批次，并处理非原子提交

点击“运行自动化测试”时，前端生成一个 UUID `testBatchId`，按源端和目标端各创建一个测试请求，明确指定 `SOURCE`/`TARGET` 角色，且不发送 `environmentId`。两个请求成功后立即刷新测试历史和比较记录。

现有 API 是两个独立创建请求，没有批量原子端点。若其中一个请求失败，界面必须保留已创建的一侧任务、提示另一侧失败，并允许用户使用相同配置重新发起一整批；不得伪造“已比较”的状态。

### 4. 比较结果只读并由测试批次关联

Drawer 根据 `testBatchId` 查询比较记录，在一侧未结束时显示“等待两侧测试完成”，在比较任务运行时显示进行中，完成后展示总体结论、风险等级、摘要和不可用原因。比较详情与代理输出可进入二级详情视图。

不提供“开始比较”按钮，因为服务端会在配对测试均为终态后自动调度比较；手动触发会重复已有编排并使前端状态难以解释。

### 5. 日志与构建日志保持相同的二级 Drawer 交互

点击某侧测试的日志，打开嵌套 Drawer 展示任务概要和日志事件。日志正文使用可换行、可复制的只读文本块，不使用 CodeEditor；这避免嵌套 Drawer 内编辑器高度计算造成内容无法撑开的现有问题。

## Risks / Trade-offs

- [两侧构建不是同一当前源码或任一侧已过期] → 禁用运行操作，明确标出缺失/过期的一侧，并引导用户回到构建节点完成构建。
- [两次创建请求只有一次成功] → 展示部分已创建的测试，不显示比较结论；刷新历史并允许同配置重新运行一个全新批次。
- [后端不产生可用的 passed/failed/skipped 聚合计数] → 保留退出码、任务状态和日志作为可信结果，计数显示为 `--`，不推导用例级结论。
- [自动比较服务不可用或结果尚未生成] → 直接展示后端状态与不可用原因，不能把它误报为测试失败。
- [构建目录在两端不同] → 在两侧前置条件卡中分别显示派生目录，测试配置只保留共享字段。

## Migration Plan

1. 发布前端节点和 Drawer，复用已部署的自动化测试与比较 API。
2. 通过现有构建记录验证：两侧成功构建、单侧缺失、运行中、测试失败和比较不可用场景。
3. 若出现前端兼容问题，将测试节点恢复为延后状态；后端接口和既有测试记录不受影响。

## Open Questions

- “当前源码”的判定在前端应以当前 source revision ID 为唯一条件，还是还要匹配源码部署记录版本；实现前需以现有构建列表字段验证可用性。
- 当一批测试只创建成功一侧时，产品是否需要在历史中提供“补齐另一侧”的精确重试，还是仅提供重新运行完整批次；本变更默认后者。
