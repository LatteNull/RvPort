## Context

工作流已经包含 `x86-build -> rv-dependency-analysis -> report` 的节点和连线，但两个节点目前共用 `BuildReadiness` 静态演示 Drawer。后端已提供构建运行、源码部署、项目级运行环境和依赖分析的完整模型：依赖分析创建时会要求当前源码版本存在成功的 `SOURCE_ONLY` x86 构建，并自动使用项目级 RISC-V 目标环境。

## Goals / Non-Goals

**Goals:**

- 将 x86 构建和依赖分析实现为独立、真实数据驱动的 Drawer。
- 固定 x86 构建为 `SOURCE_ONLY`，不暴露用户可切换的构建范围或环境选择。
- 让依赖分析明确显示其输入的源码版本、成功 x86 构建与 RISC-V 目标环境，并以服务端分页展示结果和历史。
- 使用任务状态和手动刷新呈现异步执行过程，保持记录与当前项目级运行环境版本的可追溯性。

**Non-Goals:**

- 不修改构建、源码部署、依赖提取、依赖匹配或任务执行的后端逻辑。
- 不实现 RISC-V 完整构建；该能力仍属于后续的构建验证节点。
- 不在两个节点中允许临时修改项目级源/目标环境。
- 不增加轮询；用户通过刷新获取最新任务状态和结果。

## Decisions

### 拆分两个 Drawer，而非扩展静态 BuildReadiness

`x86-build` 与 `rv-dependency-analysis` 共享前后关系，但它们的创建请求、结果数据和操作不同。分别建立 `X86Build` 和 `DependencyAnalysis` 目录，保留共享的展示原子组件或状态映射，避免用条件分支把不同领域模型混入一个容器。

替代方案是保留单一 `BuildReadiness` 并以 stage id 区分视图。该方案会继续混合构建运行与依赖结果类型，且难以清除演示状态，故不采用。

### x86 构建固定为 SOURCE_ONLY

x86 构建创建请求固定携带 `buildScope: SOURCE_ONLY`，使用当前激活源码版本和项目级 x86 源环境。Drawer 显示但不编辑这两个输入；构建命令、工作目录、超时和环境变量遵循既有构建 API。

替代方案是让用户选择构建环境或 `BOTH` 范围。此方案会使“x86 构建”与完整构建验证重叠，并破坏依赖分析对源构建的明确前置条件，故不采用。

### 依赖分析以成功 x86 构建为硬前置

依赖分析创建仅提交可选的源码版本标识，后端负责定位当前项目级运行环境、同版本成功 x86 构建和目标环境。前端在没有可用构建时禁用操作并引导用户进入 x86 构建；不允许手选构建记录或目标环境。

这保持前端与后端的可重复性约束一致，也避免用户把一个旧构建误用于当前源码。

### 结果、历史与失效状态由服务端记录驱动

两个 Drawer 使用现有列表、详情、结果和产物接口。历史与依赖结果使用 `BaseTable` 服务端分页、筛选和排序；运行中与完成后由显式刷新更新。当前源码版本或项目运行环境版本变化时，UI 使用后端返回的版本字段将历史记录标识为非当前，不把旧结果作为当前结论。

### 画布状态保持适配层

现有工作流状态数据补充 x86 构建和依赖分析的真实状态解析，保持节点顺序和边不变。状态映射不得由 Drawer 本地 state 决定，避免关闭 Drawer 后画布退回演示状态。

## Risks / Trade-offs

- [后端需要成功源码部署后才能创建构建] → 在 x86 构建前置条件中展示部署状态与明确的源码管理引导。
- [依赖分析仅接受当前版本成功 x86 构建] → 禁用分析按钮并显示缺失或已失效原因，不尝试绕过服务端约束。
- [手动刷新不会自动完成运行中任务] → 在运行状态明确展示刷新入口和最近刷新时间；不引入轮询。
- [依赖结果字段较多] → 使用固定列宽、文本截断与详情视图，保留结果表的可扫描性。
- [旧构建和分析仍可查看] → 以“非当前源码/环境配置”提示其不可作为当前阶段结论，但保留审计可见性。
