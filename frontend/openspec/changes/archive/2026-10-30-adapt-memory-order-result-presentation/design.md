## 背景

现有专项分析共用列表、详情和证据 UI；知识库也复用证据组件。内存序协议要求按主路径呈现证明，而浮点及知识库仍按自身协议消费，不能全局重排。

## 目标与范围

完成 2.0/3.0 兼容、保守分类、诊断汇总、证据图、源码切换、完整性和报告待核实语义。仅编辑前端 root；浮点 Finding 粒度在独立变更中记录。

## 设计决定

1. 展示适配只派生值，不改写 API 原始 detail、severity、verdict 或人工选择。候选、inconclusive、受限消解按 info 展示，置信度显示未评估；reason/detail 和双语回退独立于浮点 impact。
2. `analysisDiagnostics` 不使用零值兜底。内存序只有 `diagnosticsAggregated=true` 才接收明确的诊断总数；显式 null 优先于顶层旧数字。frontier 独立展示。下载复用已有制品入口，审计包完整诊断路径为 `diagnostics/full.json`。
3. 图适配建立 ID 索引，按 primaryPath 生成主链。其他节点、分支关系、断点和预算可展开。重复 ID、缺引用、未知类型、断链和环产生可见警告并降为不完整；拓扑检查使用迭代算法，不递归遍历异常环。
4. 共用证据组件只在传入内存序图元数据时增加分支/断点区域；知识库和浮点的默认步骤语义保留。
5. 内存序证据只使用所选位置带 sourceSha256 的分析时内嵌 snapshot，不复用补充接口片段。现有 codeContext 没有 digest：前端使用真实的 Finding、run、sourceRevision、文件和位置范围核对它，仅在主位置提供单独的补充阅读入口，明确未校验分析 digest，不作为证据。编辑器按需创建，切换步骤或位置时卸载补充阅读区。无源码步骤与断点保持真实缺失说明。
6. Workflow 保留 DONE 事实，同时显示部分分析警告。阶段、历史和报告通过 analysisStatus/analysisComplete 读取完整性，不从 SUCCEEDED 推导。
7. 报告中的 pendingVerification 与正式风险统计分开。人工确认仅改变报告纳入状态；UI 仍提示待核实，新 run 使用自身 Finding 的选择状态，不继承旧条目。
8. 支持正式风险的 critical 等级；候选不因原始等级高而升级。现有分页接口按原始数据库等级筛选，无法表达历史候选的派生展示等级，因此内存序页移除等级筛选并忽略旧筛选状态，保留服务端搜索及分页；浮点页保留等级筛选并增加 critical。不得以全量拉取替代服务端分页。
9. breaks.expectedKind 是开放的证据名称，不使用步骤类型枚举校验。step.kind 与 edge.kind 的未知类型检查保留。
10. 报告仅在存在内存序分析记录、内存序输入或待核实项时展示相关区域。纯知识库、纯浮点以及分析 UNAVAILABLE 且无内存序输入的报告不显示内存序警告；有内存序历史输入但缺完整性字段时明确未知。
11. 用户要求保留整体概览样式：恢复原有状态、计数与制品布局，只增加主要诊断摘要、前沿数量和“查看诊断明细”入口，完整记录不在概览内展开。诊断复用阶段内二级详情导航，记录编码、原因、建议、范围、引用、截断与下载在该页展示，正文使用阶段既有滚动容器。进入时绑定明确 run ID，复用所选执行查询，不额外建立同数据订阅；新执行产生不会替换已打开的诊断。返回保留最新/历史入口、所选历史记录、日志及筛选状态。加载失败显示重试，不转成零诊断。浮点概览保留原布局。

## 风险与限制

- 当前 codeContext 协议不提供 sourceSha256，不能在测试中模拟该不存在字段来宣称证据校验通过。补充阅读区仅核对现有身份字段，始终标注未校验分析 digest；带 digest 的证据仍只来自分析快照。
- 用户追加“验证收尾”后，已完成 Docker 内前端质量检查与生产构建，验证当前整个前端工作区；结果见 [验证记录](verification.md)。不包含部署、后端环境版本确认、真实扫描与覆盖率验收。
