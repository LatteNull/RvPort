## Context

见 [proposal.md](proposal.md) 的动机。当前 `FindingDetail.tsx` 已能读取 Scanner V2 的 `fact`、`conclusion`、`occurrences` 与 `evidenceChain`，也保留旧版投影字段和原始 `evidence` 的兼容读取；但组件将数据兼容、状态映射、位置选择和多个独立展示区域集中在一个文件中，并以左右卡片矩阵呈现。代码上下文接口只按 Finding ID 返回一个补充上下文，不接受 occurrence 参数；其他位置能否展示源码取决于 occurrence 内嵌的 `location.context.lines`。

后端 `KbScannerResult.Finding` 已定义 `primaryOccurrenceId`，但 `FindingResponse` 当前没有将其作为顶层字段返回；值仍可从保存的 `evidence.finding.primaryOccurrenceId` 读取。此次前端变更需要在不伪造后端事实的前提下提供稳定体验，并保留未来后端补齐顶层字段后的自然迁移路径。

## Goals / Non-Goals

**Goals:**

- 建立独立、纯函数式的 Finding 详情展示模型，集中处理字段优先级、枚举文案、主要位置与证据链降级。
- 让详情布局遵循单一纵向阅读路径，同时在宽屏保留代码与辅助信息的合理并列，窄屏不隐藏关键内容或操作。
- 将多 occurrence 的选择状态限制在当前 Finding 内，并确保选择变化驱动位置相关内容同步更新。
- 维持详情与代码上下文两个请求的独立失败边界，保留按需加载 Monaco 的性能边界。

**Non-Goals:**

- 不修改 Scanner 的规则、推理过程、证据链生成方式或置信度计算。
- 不为代码上下文接口新增 occurrence 参数，也不在前端读取源码文件或拼造缺失上下文。
- 不修改 Finding 列表的列、概览统计或筛选能力。
- 不引入新的 UI、状态管理或可视化依赖。

## Decisions

### 1. 先归一化为展示模型，再由组件渲染

在知识库领域的 `presentation.ts` 或同职责模块中新增纯函数，把原始详情转换为结论摘要、状态标签、位置列表、当前位置详情、证据路径与缺失说明。优先级固定为：响应顶层结构化字段 → `evidence.finding` 中的 Scanner V2 结构 → 旧版投影字段；仅在前一级缺失或为空时回退。

这样可以在无 DOM 的单元测试中覆盖契约差异，避免每个 JSX 区域各自判断字段并产生不一致文案。备选方案是在组件内继续零散回退，改动较小但会放大现有耦合，因此不采用。

### 2. 使用“结论—证据—行动”的内容结构

详情顶部使用一个克制的结论摘要区，只突出标题、原因和真正影响决策的状态。主体按主要代码证据、判断依据、处理建议向下展开；规则、事实类型、符号、发现时间等辅助元数据并入判断依据的次级区域，不继续形成多个同权卡片。

宽屏允许代码正文与当前 occurrence 的简短元数据并列，但 DOM 顺序仍遵循纵向阅读路径；窄屏回落为单列。视觉层级主要依赖留白、字号、轻柔底色和语义色，风险色只用于风险与阻塞，不新增装饰性边框矩阵。备选方案是保留现有两栏仪表盘布局，仅调整颜色与间距；它不能解决阅读顺序和信息竞争问题，因此不采用。

### 3. occurrence 选择驱动一个统一的位置视图

默认 occurrence 先匹配归一化后的 `primaryOccurrenceId`，匹配失败时选择第一个具有位置数据的 occurrence，再回退到 `fact.primaryLocation` 或旧版文件投影。切换 occurrence 后，文件范围、内嵌代码、configuration、selectionStatus 和 reasonCodes 由同一个 selected occurrence 派生，避免标题位置与代码内容不一致。

补充的 `/findings/{id}/code-context` 仅用于默认/投影位置没有内嵌源码行时的兜底，不把它错误套用到一个明确不同的 occurrence。若非主要 occurrence 没有内嵌行，只展示位置元数据和局部不可用说明。备选方案是切换时继续展示 Finding 级补充上下文，虽然内容更满，但可能把错误代码绑定到所选位置，因此不采用。

### 4. 证据链按可信度逐级降级

当 `primaryPath` 能完整映射到 steps 时展示主路径；无法完整映射时不静默丢弃步骤，而是展示服务端 steps 顺序并标注“可用证据，主路径未完整确认”。`breaks`、步骤状态和预算截断在证据区域就近呈现。原因码先通过领域映射转成中文；未知值保留原值作为可追溯信息，但不直接作为主要结论文案。

不使用流程图库绘制证据图。当前主路径是适合线性阅读的有序证据，图形化会增加交互和布局复杂度，也会让断点、候选分支在数据不完整时产生虚假的确定性。

### 5. 报告操作进入“建议下一步”，历史结果保持只读

复用现有 `MigrationInputActions` 及精确 query-key 失效策略，但把状态和操作与迁移建议放入同一行动区域。是否可操作由详情入口的 current/history 上下文决定，而不是由 Finding 自身字段猜测。历史详情继续展示当时保存的结论、证据和纳入信息，但不渲染写操作。

### 6. 按职责拆分组件而不建立跨阶段抽象

保留 `FindingDetail` 作为加载边界与组合入口，将稳定、独立的区域拆为同目录组件，例如结论摘要、代码证据、证据路径和行动区；位置选择与当前 Finding 的局部状态保持在组合层。组件只消费明确的展示模型与回调，不直接发起领域请求。所有样式仍位于知识库阶段的局部 SCSS Module，避免为一次详情改版建立过度通用的共享层。

### 7. 将位置、证据路径与代码合并为联动工作区

评审后的详情不再把 occurrence、主要代码和判断路径表现为三个彼此割裂的纵向卡片。宽屏使用“左侧判断路径、右侧代码查看器”的证据工作区，窄屏保持代码优先的 DOM 阅读顺序并回落为单列。单个 occurrence 仅展示位置摘要；多个 occurrence 使用紧凑选择器，不再为每个位置绘制大卡片。

默认代码视图优先使用 `/findings/{id}/code-context` 返回的完整有界窗口，而不是更 occurrence 内嵌的较小上下文。用户选择带 `source` 的 evidence step 后，代码视图切换到该步骤内嵌的 `source.context` 并高亮其真实行号；选择 knowledge、Classification 或 Assessment 等无源码步骤时，只更新步骤选中态和说明，保留最近一次有效代码视图。代码上下文接口仍不被误用于非主要 occurrence 或任意 evidence step。

### 8. 复用父级扫描上下文

从当前结果进入详情时复用 `GET /projects/{projectId}/kb-scans/latest` 已返回的 scan；从历史记录进入详情时复用历史结果页已加载的 scan。详情只为 Finding 与可用代码上下文建立请求，不因 view 携带 `scanId` 再次请求 `GET /kb-scans/{scanId}`。报告操作继续从父级 scan 获得 `currentSourceRevision`、`sourceRevisionId` 和列表失效键。

### 9. 用单层标题与渐进披露继续压缩详情

结论头部将风险、阻塞性和置信度作为同一组决策元信息放在标题右侧，避免状态标签散落在标题正文下方继续增加高度。证据区域只保留“证据工作区”一个总标题；代码当前模式、位置与判断路径成为同一容器内的工具信息，不再用“代码证据”重复命名同一层级。

扫描事实属于复核信息，改为默认折叠的原生 `details/summary`，需要时可完整展开。建议下一步的主要建议与报告状态、操作按钮在空间允许时同排，窄屏再自然堆叠。面板统一使用 12px 内边距，结论区使用 12px 16px，以减少空白但保持可点击面积与阅读层级。

### 10. 对齐证据双栏与次级折叠入口

宽屏证据工作区的判断路径和代码面板共享同一 Grid 行高，在不裁剪判断路径的前提下保持左右边界对齐。窄屏取消等高约束并按内容自然展开。工作区标题展示当前实际代码来源：默认是 Finding 主位置；点击带完整 `source.context.lines` 的 evidence step 后，同时切换为该步骤的文件、范围和内嵌代码，因此允许可靠地展示另一个文件中的宏定义；前端不根据只有位置而没有源码的步骤跨文件猜测或读取代码。

判断置信度以单行标签和值展示。扫描事实与原始扫描数据共享同一种 `details/summary` 标题布局、图标、展开文案和旋转箭头；报告状态与按钮放入“建议下一步”标题行，建议正文独占下一行，以稳定标题与操作的视觉关系。

### 11. 左侧概览、右侧完整阅读证据步骤

判断路径左侧负责快速定位步骤，长标题和说明使用单行省略；当前选中步骤的完整标题与说明在右侧代码区顶部展示。`edges[].kind` 继续参与路径排序与数据复核，但不在主要界面展示抽象关系标签，避免增加理解成本。判断路径取消固定高度和内部滚动，由双栏 Grid 的自然行高让两侧背景保持等高；原始扫描 JSON 则保留最大高度并在代码块内部滚动，避免诊断数据无限拉长详情页。

### 12. 行动优先并弱化次级复核入口

建议下一步紧跟证据工作区，扫描事实与原始数据放在其后，形成“判断—证据—行动—复核”的顺序。扫描事实不再使用卡片边框，折叠操作使用更弱的三级文本色；判断路径列表不保留额外容器内边距。证据步骤使用内嵌源码时不重复展示“扫描器随证据保存”等实现说明，只在补充上下文、缺失源码等需要用户理解的状态下提供提示。

### 13. 工作区以最小高度约束而非固定高度

证据双栏设置 400px 最小高度，Monaco 通过 flex 填满右侧剩余空间；内容更高时工作区继续自然增长。返回主要代码使用弱文本按钮，避免与证据步骤竞争。标题左侧保留工作区名称和当前文件，右侧将“证据类型 · 可达性”与“命中位置”组织为单行元信息。原始 JSON 编辑器自身限定视口高度，并显式让 CodeMirror 的 `.cm-scroller` 承担滚动，外层不滚动。

证据步骤底部的“查看源码 / 查看说明”只用于提示点击结果，使用三级文字色和正常字重，不作为主操作强调。

### 14. 原始数据使用确定高度的编辑器视口

原始 JSON 不再仅依赖 CodeMirror 的 `height` 字符串和外层 `max-height`。折叠内容提供一个 `min(320px, 50vh)` 的确定高度视口，CodeMirror 以 `100%` 填充该视口，并由 `.cm-scroller` 独立承担纵向与横向滚动。这样编辑器内容不会反向撑高折叠面板，滚动条也保持在代码区域内。

### 15. 统一代码编辑器高度契约

`CodeMirrorEditor` 与 `MonacoEditor` 使用相同的高度语义：调用方传入 `height` 时使用该明确高度；省略时默认 `100%` 填充父容器。两个封装都设置 `min-height: 0`，并由各自内部滚动层承担溢出。使用自适应模式的父容器必须提供可计算的高度或 flex/grid 剩余空间，避免父子双方均为自动高度。

### 16. 命中行使用背景与独立标记槽

Monaco 命中行保留淡色整行背景，并在 Monaco 预留的 `line decorations` 槽位右缘绘制橙色竖线。竖线贴近代码区但不进入正文，也不绘制在行号文字之上，从而同时保留明确的命中标记和首字符可读性。

## Risks / Trade-offs

- [后端暂未顶层返回 `primaryOccurrenceId`] → 在单一归一化函数中保留 `evidence.finding.primaryOccurrenceId` 兼容读取，并以测试记录移除条件；后端补齐后优先使用顶层值。
- [非主要 occurrence 可能没有内嵌源码] → 只展示可信的位置元数据与局部缺失说明，不复用可能属于其他位置的 Finding 级代码上下文。
- [证据步骤和原因码持续演进] → 已知枚举使用集中映射，未知值安全展示原值，避免因为新增枚举导致空白或渲染失败。
- [重排详情可能影响现有报告操作入口] → 保持 mutation 与缓存校准逻辑不变，以当前和历史两类入口测试验证权限边界。
- [长代码、长路径和大量 occurrence 增加页面高度] → 代码区域保持受控高度，位置列表允许局部滚动；核心结论和操作不因辅助内容增长而变得不可达。

## Migration Plan

1. 先增加展示模型和覆盖结构化/兼容数据的纯逻辑测试，不改变现有页面。
2. 按区域替换 Finding 详情组件与局部样式，接回现有请求、返回导航和报告操作。
3. 补充当前结果、历史结果、多位置、证据断点和代码上下文失败的组件测试。
4. 运行受影响测试、格式化检查、ESLint、TypeScript 检查和 OpenSpec 严格校验。
5. 若上线后需要回退，仅回退详情展示组件与映射；接口、缓存键和服务端数据不需要迁移。
