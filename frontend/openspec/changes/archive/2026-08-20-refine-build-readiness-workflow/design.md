## Context

当前 Workflow 在“源数据管理”后同时展示知识库扫描和环境与依赖对比；后者依赖两侧环境快照，无法直接表达当前源码的 RISC-V 构建可用性。当前画布还将多源结果先放入“迁移输入合并”，再进入评估报告；在环境对比入口隐藏后，该中间节点不再具有用户可理解的职责。

本 change 仅重组前端固定画布和节点 Drawer 的演示交互。后端尚不存在 x86 构建依赖提取、RISC-V 缺失依赖分析或构建前确认的正式契约，因此不得通过前端猜测接口或将本地示例写入服务端状态。

## Goals / Non-Goals

**Goals:**

- 用“源码分析”和“构建可用性分析”两条并行支路表达构建前信息来源。
- 将知识库扫描结果与依赖分析结果共同汇入评估报告；报告发现问题后进入人工处理并回到源码管理，满足条件时直接进入构建验证。
- 保持构建验证、自动化测试、优化闭环和归档位于既有后段主线。
- 为新增节点提供可交互、可测试的静态 Drawer 演示状态。

**Non-Goals:**

- 不新增、修改或模拟后端 API、SSE、轮询、任务创建或状态持久化。
- 不删除 SBOM Drawer、既有 SBOM 数据、构建记录或迁移输入实现。
- 不实现真实的 x86 构建、依赖提取、RISC-V 缺失依赖检测或确认失效计算。

## Decisions

### 1. 以评估报告替代画布中的迁移输入合并

评估报告是源码分析与构建可用性分析的统一用户可见汇总节点：当前由知识库扫描和依赖分析直接输入，未来 AI、内存模型、浮点等扫描也可并列输入。隐藏迁移输入合并而非删除它，因为只有在用户需要选择、去重或编排多份结果时，该中间概念才具有独立的产品价值。

### 2. 当前不设置独立的构建前确认节点

源码管理并行触发知识库扫描与 `x86 构建 → 依赖分析`。两条分析结果输入评估报告；评估报告可将问题送入人工处理并反馈至源码管理，或在条件满足时直接进入构建验证。源码对比不表达当前生命周期流转，也不在源码管理 Drawer 中提供入口。

当前没有审批、风险接受、审计或确认失效的后端契约时，独立确认节点只会重复评估报告和源码对比的结论。因此先省略该节点；未来出现这些真实业务需求时，再以“构建准入”恢复。

### 3. 新节点 Drawer 使用 feature-local 静态 model

新增 `x86-build` 与 `rv-dependency-analysis` 节点由 StageDrawer 组合入口映射到独立展示组件。静态 model 覆盖通过、待处理、已失效及空结果，并仅在组件本地切换演示状态。组件 SHALL NOT 调用领域 API、TanStack Query 或 mutation。

现有环境、源码、知识库、SBOM、构建和测试 Drawer 保持原有 API 行为；本 change 仅在画布上隐藏 SBOM 入口，不以静态数据覆盖它们。

### 4. 把静态状态与未来服务端事实隔离

静态 Drawer 明确标识为“演示数据”，并使用 source revision、x86 build 和 RISC-V 环境配置版本的示例标识说明确认范围。未来接入正式接口时，只替换 feature-local model/hook 的数据来源，不改变节点、分组、边、Drawer 路由或可见状态语义。

## Risks / Trade-offs

- [静态成功状态可能被误认为真实构建结果] → Drawer 显示“演示数据”，且不提供会造成真实任务已创建印象的执行按钮。
- [隐藏 SBOM 后用户找不到已有分析] → 只移除画布入口，不删除模块；后续可从项目历史或恢复节点进入。
- [未来扫描增多后评估报告输入变复杂] → 评估报告使用可扩展的输入边，不恢复合并节点，除非出现真实的选择/去重/编排需求。
- [当前后端双环境构建语义与画布 RISC-V 节点名称不同] → 本 change 只调整 UI 演示语义；正式 API 改造另开跨前后端 change。

## Migration Plan

1. 替换前端固定拓扑与 StageDrawer 映射，并保留被隐藏模块的代码和历史查询入口。
2. 增加静态 Drawer 和单元测试，不发出新的网络请求。
3. 若需回滚，恢复现有拓扑配置与 `sbom` 入口即可；不涉及数据库、API 或用户数据迁移。
