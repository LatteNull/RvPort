## Context

前端已有本地账号登录和已登录改密，但未登录用户缺少自助找回入口。后端已实现邮件申请与 token 确认接口，邮件链接实际指向 `/reset-password?token=<token>`。

## Goals / Non-Goals

**Goals:**

- 提供从登录页开始、无需登录态的完整重置密码流程。
- 与后端统一成功响应配合，避免通过页面反馈泄露账号是否存在。
- 复用现有 `ChangePasswordForm` 的新密码和确认密码校验，保持规则一致。
- 改密成功后执行既有退出接口并回到登录页。

**Non-Goals:**

- 不实现邮件发送、token 生成、有效性预校验或管理员重置密码。
- 不在浏览器持久化 token、密码或账号存在性信息。
- 不新增运行时依赖或全局主题样式。

## Decisions

### 使用两个访客路由

`/forgot-password` 仅提交账号或邮箱；`/reset-password?token=` 仅提交新密码。两者使用 `requireGuest`，避免已登录用户绕过当前会话进入重置流程。将 token 保留在查询参数中以兼容后端邮件链接，并只在提交时读取。

### 统一成功反馈

申请接口成功后固定显示“如账号存在且已绑定邮箱，重置链接已发送”，不依据账号是否存在改变 UI。页面不保存输入的 identifier。

### 共用密码表单校验

`ChangePasswordForm` 扩展为可隐藏当前密码字段的模式；重置页使用该模式，继续复用新密码与确认密码规则。页面仍由自身负责 API mutation 和跳转。

### 改密成功后显式退出

当前密码修改和 token 重置均在成功后调用 `POST /auth/logout`，再清除前端缓存并 replace 到 `/login`。若服务端已先行失效会话导致 logout 请求失败，前端仍必须清除本地态并跳转，保证用户不会停留在已失效的受保护页面。

## Risks / Trade-offs

- [邮件链接路径与 API 路径名称不同] → 路由按后端实际发送的 `/reset-password` 建立，并在规格中明确区分。
- [token 缺失或已过期] → 禁止提交缺失 token 的表单；后端错误由共享请求层反馈，页面保留重新申请入口。
- [共享表单增加模式] → 仅增加明确的 `requireCurrentPassword` 配置，默认保持现有改密页面行为。
