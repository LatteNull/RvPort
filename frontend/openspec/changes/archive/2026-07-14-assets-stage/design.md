## Context

`assets` 是环境管理之后的源码输入确认点，也是源码扫描之前的唯一入口。现有 `StageDrawer` 只为 `project` 和 `env` 提供专属实现，`assets` 仍落到默认详情；workflow 状态模型以单个 `currentStageId` 表示焦点，无法准确表达六条扫描支路并行运行。

原型提供当前源码、压缩包上传和 Git 更新三类信息。当前产品决策明确：首期只管理当前有效源码，不管理二进制、不保留版本历史或源码对比基线；确认版本后固定启动全部六条分析。

## Goals / Non-Goals

**Goals:**

- 为 `assets` 提供与 `Project`、`Environment` 一致的专属 Drawer。
- 让用户查看并覆盖当前有效源码，来源为压缩包或 Git 二选一。
- 通过一次确认启动 SBOM、知识库、纯 AI、内存模型、浮点精度和对齐与布局优化六项分析。
- 让固定 React Flow 拓扑正确展示并行运行状态、六条活动边和源码扫描分组焦点。

**Non-Goals:**

- 不管理二进制输入、制品下载、版本历史、回滚或源码对比基线。
- 不允许用户勾选部分扫描支路；首期始终启动全部六项。
- 不在前端模拟分析完成、上传进度或长任务状态；服务端状态为事实来源。
- 不建立 SSE；本 change 仅定义请求完成后返回的 workflow 状态刷新。

## Decisions

### 1. 使用 Drawer 子视图，而非 Drawer 上叠加 Modal

`Assets` 维护 `overview`、`upload` 和 `git` 判别式视图。概览展示当前有效源码；上传和 Git 更新是同一阶段工作区内的表单子视图，提交成功后返回概览并刷新详情。

该选择与环境管理一致，避免在已经打开的阶段 Drawer 上叠加第二层 Modal。进入子视图后隐藏右上角关闭按钮，提供返回、取消和提交操作；若表单已修改，返回时要求确认放弃。

### 2. 当前版本只保留一个来源

阶段详情返回单个 `currentArtifact`。`ARCHIVE` 来源包含文件名和版本说明；`GIT` 来源包含仓库地址与 Ref/提交标识。上传或 Git 更新均替换当前版本，不追加前端可见历史记录。

这样避免同时展示“Git main”和“源码上传包”而无法判断哪一个是扫描基线。版本历史、回滚和源码对比所需的基线在后续 change 重新设计。

### 3. 上传和 Git 更新通过领域 API 边界提交

前端在 `src/api/project.ts` 增加源码制品领域 API：读取 `assets` 阶段详情、上传压缩包、从 Git 更新和推进 `assets` 阶段。上传使用 `multipart/form-data`；其余请求使用当前 JSON API 包络。

Git 表单使用仓库地址和 Ref（分支、tag 或 commit）表达目标版本；可选凭据使用用户名加 Access Token。读取详情和 mock 不返回 Access Token 或任何敏感凭据，用户仅能重新输入覆盖。

压缩包首期仅接受 `.zip`；具体大小上限由服务端契约返回或在后续产品决策中补充。上传后的动作支持“仅更新当前版本”与“更新后启动源码分析”。

### 4. `assets` 推进固定启动六条并行分析支路

概览 Footer 的主操作为“启动源码分析”。确认后调用既有阶段推进接口；服务端校验当前有效源码存在后，将 `assets` 置为完成，并启动 `sbom`、`kb`、`ai-scan`、`memory`、`fp` 和 `alignment`。

工作流状态扩展为保留阶段状态和活动边，并增加 `focusGroupId` 与 `currentStageLabel`：本次推进返回 `focusGroupId: 'scan'`、`currentStageLabel: '源码分析 · 6 项进行中'`。前端仍维护 React Flow 拓扑和分组边界；服务端不返回节点坐标或边定义。

### 5. Query 缓存与失败恢复沿用既有模式

阶段详情仅在 `Assets` Drawer 可见时请求。上传、Git 更新和推进成功后更新或失效 `assets` 阶段详情及 workflow 状态缓存；失败时保持当前 Drawer 和表单上下文，展示业务错误。Vite mock 使用正式成功/失败包络，并覆盖无当前源码、上传失败、Git 拉取失败和不满足启动条件等场景。

### 6. 表单取消按未保存修改状态确认

项目阶段 Drawer 中的表单取消统一遵循同一规则：未修改时直接返回，存在未保存修改时才要求确认放弃。该规则同时适用于源码制品上传/Git 更新以及环境的新建、编辑和脚本表单，避免无意义确认并防止误丢失输入。

## Risks / Trade-offs

- [单一当前版本无法解释后续源码对比基线] → 首期明确不提供对比；后续 `diff` change 再引入 revision 模型。
- [六项分析并行但工作流有单一 current stage] → 使用 `focusGroupId` 和聚合 `currentStageLabel` 表示用户关注区域，避免任意选择一个运行节点。
- [上传文件可能较大] → 首期限制 `.zip` 并由服务端强制大小限制；前端使用提交 loading 和可恢复错误，不缓存文件内容。
- [Git 凭据泄露] → 只接受本次显式输入的 Access Token，不读取、不回显、不写入日志、缓存或 mock fixture。
- [自动启动分析不可逆且开销高] → 在“启动源码分析”及“上传后启动”前使用二次确认，明确六项任务范围。

## Migration Plan

1. 增加类型、API 边界和开发 mock，使 `assets` 可独立读取和更新。
2. 在 `StageDrawer` 注册 `Assets`，保留默认 Drawer 作为其他未实现阶段的回退。
3. 扩展 workflow 状态消费以支持分组焦点和聚合当前阶段摘要。
4. 为上传、Git 更新、推进和并行状态映射增加组件/逻辑测试。

回滚时移除 `assets` 注册即可恢复默认 Drawer；新增 API 和状态字段采用可选读取，不影响未升级服务端的既有节点拓扑。

## Open Questions

- `.zip` 的最大文件大小、服务端是否支持断点续传及取消尚未确定；首期以服务端拒绝反馈为准。
- Git 认证是否需要支持 SSH 私钥，还是首期仅支持公开仓库和用户名加 Access Token，尚待后端契约确认。
