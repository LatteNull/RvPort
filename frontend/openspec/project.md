# RvPort-Frontend 项目规则

## 1. 项目使命与边界

RvPort-Frontend 是 x86 到 RISC-V 迁移平台的前端应用，位于 monorepo 的 `frontend/` 目录。它负责将项目创建、迁移流水线、环境管理、问题与结果等后端能力组织为可理解、可操作、可验证的 Web 界面。

本文件定义前端开发的长期工程约束：架构边界、实现规范、测试策略和交付验证。下文“必须／不得”约束后续新增或修改的代码，不表示所有存量页面已经满足。已交付行为由当前能力规范描述；待实现行为只进入 change，不写入当前能力基线。

项目定位与视觉方向遵循 [AGENTS.md](../AGENTS.md)：面向个人用户的迁移门户，以任务进展、结论和下一步操作组织界面。Ant Design 提供交互基础，不能替代产品设计。

前端 OpenSpec 根目录为 `frontend/openspec/`。前端 change 默认只能影响 `frontend/`；跨前后端的契约变更必须明确说明影响范围并与相关项目的规范保持一致。

## 2. 决策与事实来源

当前能力基线位于 `openspec/specs/`，入口与职责索引见 `openspec/specs/README.md`。该基线按当前已交付能力整理；未完成、已移除或已被替代的行为不保留为有效要求。实现前必须核对相关规范、代码与测试，不得从历史规划自行恢复功能。

### 冲突与变更处理

- 用户在当前任务中的明确指令优先。产品方向与代码组织遵循 `AGENTS.md`；本文件通过引用复用，不重复维护行数阈值、目录拆分等规则。
- 当前行为以主规范为基线；已明确采用的活动 change 仅在其声明范围内定义目标差异，不能据此声称目标已经交付，也不自动豁免工程约束。
- 规范与实现不一致时，结合对应测试、实际后端契约和变更记录判断：过时描述修正文档，实现缺陷修复代码，新增需求进入 change。不得仅因代码存在某行为就将缺陷固化为需求。
- 同一行为只在一个能力规范中维护。其他规范或规则文档引用其职责，不复制 API 字段、事件节流数值或业务验收场景。
- 历史产品文档、原型和 Figma 不自动覆盖当前基线，不据此恢复已删除的功能、布局或入口。后端接口文档也必须与实际契约核对后使用。
- 前端 OpenSpec 文档默认使用中文；包名、API、路径、代码标识符、协议字段和 `SHALL` / `MAY` 等关键字保留原文。

## 3. 技术基线与架构边界

### 技术基线

依赖版本与可执行命令以 `package.json`、锁文件和配置为准；以下为当前主要技术选型，不替代依赖清单。

- React 19、TypeScript 6、Vite 8、pnpm。
- Ant Design 是通用 UI 组件库；编辑器、流程画布等专用组件沿用现有技术选型。
- React Router 8 负责路由和 loader/guard。
- TanStack Query 5 管理服务端状态。
- Zustand 5 管理客户端本地状态。
- Axios 1 通过共享请求客户端访问 API。
- SCSS Modules 管理局部样式；Vite 通过 API 代理连接真实后端。
- ESLint、Prettier、TypeScript 与 Vitest 分别承担静态检查、格式检查、类型检查和单元测试；当前未配置 Husky，不把 Git hooks 当作已存在的质量门禁。

### 状态与数据边界

- 服务端拥有的数据必须通过 TanStack Query 的 query 或 mutation 管理；页面不得自行用 `useEffect + useState` 重建请求、加载、失败和缓存生命周期。
- 仅保留在浏览器侧且跨组件共享的状态使用 Zustand。认证状态、服务端缓存和临时组件状态不得混放。
- HTTP 请求必须经 `src/api/request.ts` 和领域 API 模块发出；页面和组件不得直接配置 Axios。
- 前端维护展示拓扑、布局和交互状态；后端维护项目、任务、会话和执行结果等领域事实。前端不得把展示结构反向当成服务端领域模型。
- 本地开发不提供业务 Mock 模式。单元测试使用隔离的 mock/fixture，不将测试替身注册为开发或生产接口。

### 路由与认证边界

- 路由定义位于 `src/router/`；认证和访客访问控制通过 React Router loader/guard 处理。
- 认证模型是后端 Cookie Session，不得在前端恢复或依赖 Bearer token 模型。
- 受保护页面不得各自实现独立鉴权、重定向或会话刷新逻辑；应复用共享认证状态和路由 guard。

## 4. 代码与界面实现规范

### 目录与模块

- 页面位于 `src/pages/<page>/`；页面私有组件位于其 `components/` 子目录。
- 跨页面复用的视觉或交互单元位于 `src/components/`；共享布局位于 `src/layouts/`。
- 领域请求位于 `src/api/`，领域与共享类型位于 `src/types/`，路由位于 `src/router/`，本地全局状态位于 `src/store/`。类型按领域拆分，保持单一权威定义。
- `@` 始终解析到 `src`。新增模块必须保持依赖方向清晰：页面可以依赖共享层，共享层不得反向依赖具体页面。
- 页面组合、Hook、query-key 工厂、领域类型、跨阶段复用与测试位置遵循 [AGENTS.md 的代码结构规则](../AGENTS.md#代码结构规则)。避免机械拆分微组件，也不得在页面入口、请求客户端或全局 store 中堆叠无关领域逻辑。
- 通用视觉组件通过明确类型的 props 接收数据、回调和插槽；领域 API 的选择与缓存刷新由页面或功能模块负责，不能下沉到通用组件。
- 组件 props 必须表达该组件的业务契约，而非上层 controller 的字段清单。超过约 8 个相互独立的 props，或出现多层逐字段透传时，应按共同变化的业务职责聚合为明确的领域 model/action 对象，或拆分视觉职责；不得将完整 controller、hook 返回值或无边界的 `...props` 直接下传。仅在单个基础字段有明确独立语义时保留直接 props。
- 对重要、复杂或非直观的业务规则、权限顺序、状态流转、兼容分支和清理逻辑，应使用简短中文注释说明“为什么这样做”及必要的约束；不得为直白赋值、普通 JSX 或样式声明添加重复代码语义的注释。
- JSX 仅为组织多个节点而不需要真实 DOM 容器时，必须使用显式导入的 `Fragment`；不得使用空标签 `<>...</>`，以保持结构意图可搜索且统一。

### UI 与样式

- 通用 UI 复用 Ant Design 和现有共享组件，不引入第二套通用 UI 库或主题体系。编辑器、画布等专用组件不属于第二套通用 UI 库。
- 全局 Ant Design 主题仅在 `src/theme.ts` 集中维护真正具有全局意义的 token 和组件 token，避免形成平行设计系统。
- Ant Design 已启用 `cssVar`。SCSS Modules 可使用稳定的 Ant Design CSS 变量，例如 `--ant-color-bg-container`、`--ant-color-text`、`--ant-color-text-secondary`、`--ant-color-border`、`--ant-color-primary` 和 `--ant-border-radius`。
- 不新增 `src/styles/variables.scss` 或平行的 `--rvport-*` token 层，除非有专门的 OpenSpec change 定义完整设计 token 系统。
- 修改 Ant Design 默认视觉时，优先使用 `ConfigProvider` token、component token 与组件的语义化 `styles` / `classNames` 插槽；不得将 `.ant-*` 内部选择器作为常规定制手段。
- 页面布局、业务组合、响应式和交互状态使用对应 SCSS Module。选择器必须以本地页面或组件根节点为作用域，并通过嵌套组织子元素、变体与 hover/focus 状态；避免裸元素选择器和可能跨功能泄漏的宽泛 `:global` 规则。
- 新 UI 必须处理加载、空数据、错误、禁用和进行中状态；不能只实现成功路径。

### 可访问性与交互一致性

- 新增可交互元素必须具有可访问名称，并支持与其语义相符的键盘操作；图标按钮必须提供可识别的文本标签或 `aria-label`。
- Modal、Drawer 和其他临时浮层必须提供明确的关闭、确认和取消路径，正确管理初始焦点与关闭后的焦点回归，并在危险或不可逆操作前提供确认。
- 展示可刷新领域数据的一级 Drawer，Header 右侧必须以图标按钮依次提供刷新和关闭操作；图标按钮必须具有 `aria-label` 与悬浮说明，不得以普通文字按钮替代。
- Drawer 内层视图必须明确区分“返回上一级”与“关闭整个抽屉”。关闭入口、Esc、蒙层及未保存内容保护由对应能力或 change 明确，不能把“二级页面一律禁止关闭”当作当前统一行为；具体默认能力见 [common-ui](specs/common-ui/spec.md)。
- 信息字段若没有详情页或其他明确入口可查看完整内容，当前页面必须完整展示其值，必要时允许换行、扩展行高或调整分栏；不得仅以省略号截断并依赖 Tooltip 补全。仅当完整内容已在详情页或其他明确入口可查看时，才允许使用省略显示，并必须提供组件级 Tooltip。
- 当空状态用于引导用户创建首个资源、任务或记录，创建主操作必须紧跟空状态说明展示；不得仅放在 Drawer Footer、页面其他区域或依赖用户自行寻找。已有资源后的重新创建、重试等持续性操作可按页面结构置于 Footer。
- 表单必须将字段标签、校验信息和错误反馈关联到对应控件；不得只依赖颜色、图标或占位符传达必需状态。
- 相同行为在不同页面中应使用一致的文案、禁用规则、加载反馈与成功/失败反馈；差异必须由业务语义而非局部实现决定。

## 5. API 契约

响应包络、分页、Cookie Session、CSRF 和通用失败处理由 [request-client](specs/request-client/spec.md) 维护；路由与会话行为见 [frontend-application-foundation](specs/frontend-application-foundation/spec.md)。本文件不重复维护字段或错误码清单。

- `src/api/request.ts` 负责拆包和通用失败处理；领域 API 使用 `request.get<T>()`、`request.post<T>()` 等共享客户端边界，不使用 `request.get<unknown, T>()` 等 Axios 泛型绕过类型约束。
- 契约变更必须说明前后端影响，并同步更新领域类型、API 模块、相关 fixture、测试和所属规范。兼容分支集中在请求或领域适配边界，不散落到页面。

### API 契约与测试替身

- 当前能力规范与后端契约共同确定领域类型、API 模块和测试 fixture，不得各自猜测字段、枚举或状态流转。
- 每个新增或变更接口必须在对应 change 中说明请求、成功响应、失败语义、认证要求和前端可见状态，并同步更新类型和覆盖该接口消费行为的测试。
- 测试替身应覆盖成功、空数据、权限失败和可恢复业务失败；不得通过虚构响应掩盖未确认的后端契约。

### 敏感数据与安全边界

- 真实密码、私钥、会话 Cookie 等秘密不得写入日志、浏览器持久化存储、URL、分析事件或测试 fixture。服务端错误详情按允许展示的字段处理，不直接暴露完整原始内容。
- 隔离测试可以使用明确虚构、不能访问真实服务的凭据占位值；不得复制真实用户数据、会话或环境秘密。
- 前端只保存支撑当前交互所必需的数据。认证状态遵循 Cookie Session 边界，不得在客户端复制、派生或展示服务端不应暴露的凭据。
- 需要编辑敏感信息的表单必须避免回显已保存的秘密；仅允许用户本次显式输入的值参与提交。

### 错误处理与可观测性

- 用户可见的请求、提交、路由加载和异步操作必须提供明确的加载、成功、失败和重试/恢复路径；不得只在控制台输出错误后保持无反馈状态。
- 用户提示必须使用可理解的业务文案，不泄露服务端堆栈、内部地址、凭据或完整错误详情。服务端返回 `traceId` 时，应在适当的错误上下文中保留其排障价值。
- 通用请求错误、认证失效和全局反馈应复用共享边界；页面只处理其领域特有的恢复操作。不得在多个页面复制不一致的错误解析与跳转逻辑。
- 生产代码不得遗留用于排障的 `console.log`、临时 mock 分支或吞掉异常的空 `catch`。无法恢复的异常必须被重新抛出或转换为已定义的错误状态。
- 引入错误上报或监控平台时，必须通过统一可观测性边界采集异常、路由上下文、版本和可安全传输的 `traceId`；采集策略不得包含敏感数据、完整请求体或凭据。上报失败不得影响用户主流程。

## 6. Change 与交付治理

- 每个 change 必须明确能力范围、受影响页面/状态/API 边界、非目标和验证方式；不得借无关 change 混入功能或重构。
- 新增或修改可观察业务行为时，必须在同一 change 中同步新增或更新相应测试。仅重构且不改变可观察行为时，不强制新增测试，但不得破坏既有测试。
- 交付说明必须报告实际运行过的验证命令与结果。不能执行的验证必须写明外部阻塞、未验证范围和后续补救方式。
- 不得通过删除、跳过、弱化测试或降低断言标准来掩盖失败。确有外部阻塞时，必须保留测试意图并显式说明。
- 新增或移除依赖时，默认先说明包名、用途、替代方案和影响，由用户执行 `pnpm add/remove`；只有用户明确授权时才可代为安装或移除。
- 用户明确要求创建 Git 提交时，必须遵循可用 `git-commit` skill 的流程：先核对状态和实际 diff，再按单一逻辑变更分组暂存，使用 Conventional Commits 格式生成不超过 72 字符的中文祈使句摘要；不得提交敏感文件、跳过 hooks、修改 Git 配置或执行强制推送。

### 依赖治理

- 新依赖必须优先复用现有技术栈能力；引入前应说明解决的问题、包体积或运行时影响、维护状态、许可证风险与不引入时的替代方案。
- 不得为了单一页面的局部需求引入与现有库重叠的运行时框架、状态库、路由库、UI 库或请求库。
- 依赖升级、移除或安全修复必须在对应 change 中说明兼容性影响，并更新受影响的构建配置、类型和测试。

## 7. 性能与资源边界

- 大型或浏览器能力依赖（例如 Monaco、React Flow）必须按需加载，不得因首屏渲染无条件下载；相关 change 必须说明加载触发点与失败降级行为。
- 列表、表格、画布和轮询/刷新逻辑必须根据预期数据量与更新频率选择合适策略。若存在大量数据、持续刷新或复杂布局风险，change 必须说明假设、限制和缓解方案。
- 不得在渲染路径中重复创建昂贵计算、重复发起相同请求或为纯视觉交互频繁写入服务端状态。性能优化必须优先保护正确性、可访问性和可维护性。

## 8. 长任务与实时状态

项目上下文和项目事件由 [project-overview-current-context](specs/project-overview-current-context/spec.md) 维护；readiness、latest、历史记录及缓存刷新所有权由 [project-stage-runtime](specs/project-stage-runtime/spec.md) 维护；任务日志由 [task-log-viewer](specs/task-log-viewer/spec.md) 维护。阶段开发复用这些边界，不另建互相冲突的状态体系。

- 扫描、分析、构建、测试、上传和制品处理等长任务必须以服务端任务状态为事实来源。前端负责提交、展示、订阅、重试与恢复，不得在本地伪造任务完成或用页面状态替代服务端状态机。
- 新增长任务能力的 change 必须定义任务状态、进度/结果数据、失败与取消语义、刷新或订阅策略、断线恢复策略，以及用户离开页面后重新进入的行为。
- 实时更新（包括 SSE、轮询或未来的其他协议）必须封装在共享任务/事件边界中，具备连接生命周期、去重、重连、退避、错误反馈和资源释放策略。页面不得各自维护不可控的实时连接。
- 实时事件只能用于更新服务端已有事实的前端视图；收到未知、过期或乱序事件时必须安全降级为重新获取权威状态，而不是损坏本地状态。

## 9. 文件与制品管理

- 文件上传、下载、预览、脚本、日志、报告和其他制品必须以服务端返回的制品标识、元数据和权限为事实来源；前端不得把文件内容或长期制品状态持久化到浏览器存储。
- 涉及文件或制品的 change 必须定义允许类型、大小/数量边界、上传进度、取消/重试、失败反馈、访问权限，以及成功后制品的可追溯入口。
- 真实敏感文件内容、临时下载凭据、私钥、日志秘密和用户本地绝对路径不得进入前端持久化状态、错误上报、测试 fixture 或未授权页面。测试使用虚构文件内容与路径。
- 大文件、文本预览和长日志必须按需加载或分页/截断展示，避免一次性读入、渲染或下载超出页面能力的数据。无法预览的制品必须提供明确的下载或失败说明。

## 10. 运行时配置、兼容性与展示约定

### 运行时配置

- Vite 环境变量属于开发或构建时配置，不能描述为部署后可动态修改的运行时配置。当前 API 代理目标由 `vite.config.ts` 读取 `VITE_API_PROXY_TARGET`，未配置时使用本地 `http://127.0.0.1:8080`。
- 配置集中在明确边界读取；页面、组件和领域 API 不得散落读取环境变量或硬编码环境地址。需要部署后动态配置时，必须在 change 中定义加载、校验和失败处理机制。
- 前端构建产物可读取的 `VITE_*` 值不是秘密。密码、私钥、服务端令牌和任何仅限服务端的配置不得写入前端环境文件、构建变量或源码。
- 新增配置项必须说明用途、预期格式、开发默认行为、生产必填性和缺失时的失败方式；不得以隐式回退连接到未知环境。

### 浏览器兼容与响应式

- 前端默认面向现代 evergreen 桌面浏览器。依赖特定浏览器 API、实验性 CSS 或设备能力的 change 必须说明支持范围、特性检测方式和不可用时的降级行为。
- 页面宽度统一使用 Ant Design 的 `xl`、`xxl`、`xxxl` 三个桌面断点：1024–1199px 是紧凑桌面兜底，1200–1599px 是标准桌面，1600–1919px 是宽屏桌面，1920px 以上是超宽屏桌面。紧凑差异使用 `max-width: 1199px`，宽屏和超宽屏差异按需使用 `min-width: 1600px` 与 `min-width: 1920px`；`prefers-reduced-motion` 等用户偏好查询不受此限制。
- 主布局最低宽度为 1024px。低于该宽度时保持 1024px 桌面结构并由文档页面提供横向滚动，不隐藏关键信息、不切换移动版组件，也不将主要区域重排为手机单列。
- 紧凑桌面只能收窄间距、导航和允许压缩的网格，必要时由表格、代码或日志区域提供局部横向滚动；标准桌面使用默认布局；宽屏增加工作空间，超宽屏通过内容最大宽度和外侧留白限制阅读行长。普通页面统一使用 `1600px` 内容上限，项目工作台使用 `1920px` 内容上限。

### 时间、语言与展示格式

- 用户界面默认使用简体中文；新增用户可见文案必须集中于合适的领域/组件边界，避免同一业务状态在不同页面使用不一致翻译。
- 接口时间保留带时区或偏移量的 ISO 时间语义。当前共享 `src/utils/display.ts` 使用浏览器时区格式化，不保证统一为 `Asia/Shanghai`。需要固定业务时区时，在 change 中明确展示范围并同步格式化实现和跨时区测试，不仅修改文档。
- 日期、时间、时长、数字、文件大小、状态文本和枚举展示应复用共享格式化规则或领域映射；不得在多个页面复制彼此不同的格式逻辑。

## 11. 单元测试策略

- 单元测试是功能交付的必要验证，不是功能完成后的可选补充。其目标是快速、隔离、可重复地验证前端业务行为。
- 优先级依次为：纯逻辑与数据转换、状态与路由边界、请求/缓存处理、用户可见的组件交互。端到端、视觉回归与第三方库自身行为不属于单元测试范围。
- 断言必须面向业务结果、可访问性角色、可见文本、状态变化和回调结果；不得依赖 Ant Design、React Flow、Monaco、Axios 等第三方库的内部 DOM、className 或实现细节。
- 测试不得依赖真实后端、真实浏览器会话、外部 CDN 或其他用例遗留状态。外部边界应被 mock；每例后必须清理 DOM、mock、浏览器存储、计时器和共享 store。
- 测试名称必须表达被验证的业务行为和条件。fixture 应保持最小且场景专用，避免复制大段无关接口或页面数据。
- `pnpm test` 是非 watch 的交付验证命令，必须以退出码反映结果。watch 模式只服务本地开发，不能替代交付验证。

## 12. 验证矩阵

以下命令在 `frontend/` 执行。有对应活动 change 时校验该 change；直接维护项目规则或主规范时使用主规范校验，不为文档纠错强建 change。纯文档改动不运行应用测试或构建。

| Change 类型                              | 必须验证                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------ |
| 仅 OpenSpec change 文档                  | `openspec validate <change> --strict`，以及改动文档的格式检查                              |
| 项目规则或当前能力基线维护               | `openspec validate --specs --strict --no-interactive`，以及改动文档的格式检查              |
| 前端源代码（无可观察行为变更）           | 适用的 OpenSpec 校验、`pnpm format:check`、`pnpm lint`、`pnpm typecheck`、既有 `pnpm test` |
| 新增或修改可观察前端业务行为             | 上述所有命令，外加同步更新的单元测试与非 watch `pnpm test`                                 |
| 构建配置、依赖、路由懒加载或生产产物变更 | 上述适用命令，外加 `pnpm build`                                                            |

验证失败必须修复后再交付；如因外部阻塞无法修复或运行，交付说明必须清楚区分“已通过”“未运行”和“已知失败”，不得将未运行表述为通过。
