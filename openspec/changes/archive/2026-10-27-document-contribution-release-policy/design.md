## Context

根目录当前提供中英文 README、开发指南及协作约定，但没有完整的提交与发布协作规则。此次变更依据会议纪要及用户后续修订：实际提交类型使用简写，并增加 `docs`。

## Goals / Non-Goals

**Goals:**

- 使贡献者能从 README 找到完整规范，并让 AI 协作规则与人工贡献流程一致。
- 明确提交、审计、开发集成、版本命名和计划交付之间的关系。

**Non-Goals:**

- 不改业务代码或版本元数据，不执行 Git 提交、推送、分支切换、保护设置或实际发布。
- 不建立 CI、Issue/PR 自动化，也不修改本地 `.agents/` skill。
- 不全面修订历史 OpenSpec 中与当前架构不一致的旧要求。

## Decisions

1. **以开发指南承载完整规则。** 在 `docs/开发指南.md` 增加协作与发布章节；README 提供五项规则摘要与指南链接，AGENTS 记录必须执行的核心约束和链接。相较独立新建贡献文档，这样可复用已有入口，减少重复内容。现有英文对应文档同步翻译新增章节，保留其语言入口；OpenSpec 新文档用中文。
2. **七种固定类型。** `feat` 对应新功能，`test` 对应测试，`fix` 对应缺陷修复，`refactor` 对应不改变外部行为的重构，`ci` 对应 CI/CD 配置，`chconf` 对应非 CI 的项目、构建或运行配置，`docs` 对应文档。混合变更按主要目的选择类型；会议中的长名称仅解释含义，不作为可用类型。列出 `ci` 不代表恢复已退役设施。
3. **双语标题与正文示例。** 标题采用 `<type>: <English> / <中文>`，正文按英文段落、中文段落组织，说明变更和验证。例如 `docs: Document contribution rules / 补充贡献规范`。不添加未讨论的 scope 或自动化校验工具。
4. **统一 PR 审计路径。** fork 是在代码托管平台创建个人副本，再 clone 到本地；从上游 `dev` 创建主题分支，推送个人 fork 后向上游 `dev` 发起 PR。AI 代码同样由审查者检查正确性、风险、测试与适用验证证据，自动检查通过不能代替审查。`master` 用于发布，Roadmap 完成后由 `dev` 经发布 PR 合并。
5. **四段版本明确示例。** 文档使用 `<major>.<minor>.<bugfix>.<hotfix>[-<类型><序号>]`，如正式版本 `1.2.0.0` 与候选版本 `1.2.0.0-rc1`、`1.2.0.0-rc2`。四段格式不称为 SemVer；不扩展未约定的版本递增算法或其他类型集合。
6. **Issue 完成与发布分离。** Roadmap 计划确定后创建带负责人的 Issue，PR 明确关联 Issue；在 PR 合并至 `dev` 且验收完成后关闭 Issue，Roadmap 整体完成后进入 `master` 发布。由于 `dev` 未必是默认分支，不保证关闭关键字会自动生效，必要时人工确认关闭。

## Risks / Trade-offs

- 多入口文字漂移 → 开发指南保存完整规则，其他入口保持摘要，逐项核对中英文同义。
- 被误认为已配置分支保护或自动关闭 Issue → 明确为协作规范，不声称远端设置或自动化已生效。
- 文档类型被误当成跳过代码验证的方法 → 类型由实际修改决定，带可执行代码的变更仍遵守原测试要求。

## Validation

实施后检查七种类型、双语示例、分支方向、四段版本与完整 Roadmap 闭环，验证新增相对链接及锚点、`git diff --check` 和 `openspec validate document-contribution-release-policy --strict`。纯文档无可执行代码，单元测试和覆盖率不适用；不以已有运行报告宣称本次代码验证通过。

## Migration Plan

通过 apply 更新六份文档并记录校验结果，用户要求后再 sync 与 archive；撤销时仅回退本变更的文档段落。实际提交、推送和发布不属于本次操作。
