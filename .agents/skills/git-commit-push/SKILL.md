# 提交并推送项目变更

完成用户要求的提交与推送，不只提供命令。明确调用本技能或明确要求提交并推送即授权这些操作。仅要求总结或拟定提交信息时，不暂存、提交或推送。创建或修改本技能本身不构成执行提交与推送的授权。

## 修正安全的命令构造错误，遇到真实故障停止

- 对代理编写的只读检查或验证命令，若错误明确来自选项拼写、引号、Shell 语法、工作目录或显式引用的可选路径不存在，可修正后重试一次；不能扩大原定路径或检查范围。
- 修正后仍失败，或失败命令可能已经改变仓库或外部状态时，停止并让用户决定后续处理。
- 编译、构建、测试、lint、formatter、hook 失败，冲突、异常仓库状态、远程分支前进、认证或权限问题、网络故障以及推送拒绝均为真实故障。除下述空白修复外，在首次此类故障处停止，即使看起来是临时故障也不自动重试。
- 故障后只进行描述当前状态所必需的只读检查。报告失败操作、相关错误输出、已成功步骤，以及变更处于未暂存、已暂存、已提交还是已推送状态。
- 不擅自修复、绕过或回滚故障；不自动 pull、merge、rebase、解决冲突、中止或继续已有 Git 操作、切回分支、stash、取消暂存、restore、reset、clean、amend、跳过 hook、修改 Git 配置、更换远程或强推。
- 可以给出明确的安全处理选项，但须等用户选择或授权恢复操作。已成功的步骤保持原状：提交失败后保留暂存内容，推送失败后保留本地提交。

### 唯一自动修复：行尾空白和文件末尾多余空行

- `git diff --check`、formatter、linter 或提交 hook 报告计划提交文件中的行尾空格、制表符或文件末尾多余空行时，直接修复，无需额外确认。
- 仅移除报告行的行尾空白，或删除报告的末尾多余空行并保留一个终止换行符。不重排周围代码、不转换换行格式、不整体重写文件、不修改无关文件。
- 检查修复后的 diff，必要时仅重新暂存受影响的计划提交文件，再运行原检查或提交步骤。最终报告说明此项清理。
- 同一检查修复后仍失败，或同时报告其他问题时，立即停止。

## 确定分支与远程

- 用户明确指定的分支、拉取校验远程或推送远程优先；明确只指定一种用途时，不改变另一种用途的默认规则。
- 未指定分支时，使用当前检出的本地分支名称作为目标分支，不固定为 `master`、`main` 或 `dev`。处于 detached HEAD 时停止，请用户指定分支，不猜测目标。
- 拉取校验优先使用名为 `upstream` 的远程；未配置该远程时使用 `origin`。推送优先使用名为 `origin` 的远程；未配置 `origin` 时才使用当前分支已配置的 tracking remote。若对应远程均未配置，停止并请用户指定。名为 `upstream` 的远程与分支的 tracking/upstream 配置是不同概念，不能混淆。
- 拉取校验和推送均使用目标分支的同名远程分支。不能因 tracking branch 指向其他分支，就默默改推那个分支。
- 在改变历史或推送之前，对拉取校验远程执行 fetch，检查同名分支与本地目标分支的关系。若本地落后或分叉，报告差异并停止，等待用户决定如何整合；不自动 pull、merge 或 rebase。
- 推送远程与拉取校验远程不同时，还须单独 fetch 推送远程，记录推送目标的状态。不能只校验 `upstream`，就假定 `origin` 未发生变化。若本地落后于推送目标或与其分叉，同样停止。
- 上述远程回退仅适用于远程未配置；已选远程的 fetch、认证、网络或权限操作失败时，按故障规则停止，不自动切换远程绕过。拉取校验远程缺少同名分支时明确报告；若它不同于推送远程，停止并请用户明确校验目标。推送远程缺少同名分支时，将创建该分支纳入待推送范围检查。
- 在目标分支上创建提交，不把无关的本地分支直接推到目标分支。用户明确指定另一分支时，只在 Git 能完整保留工作区变更的情况下切换；本地分支不存在而远程分支存在时可创建 tracking branch。切换不安全或受阻时停止，不自动 stash、丢弃或搬迁变更。
- 创建新提交前，检查本地目标分支上已有、但推送目标尚未包含的提交。不得默默一并推送：只有这些已有提交已明确属于用户授权范围时才继续，否则询问用户。新建远程分支时也应检查将发布的已有历史范围。

## 检查并总结变更

1. 阅读适用的仓库指令，检查 `git status --short --branch`、暂存与未暂存 diff、变更统计及相关未跟踪文件内容。
2. 只有用户要求提交当前或全部变更时，才将全部当前变更纳入范围；否则仅暂存本次请求涉及的文件。保留无关用户变更。
3. 不擅自 reset、clean、丢弃、覆盖变更或 amend 已有提交。
4. 暂存前检查凭据、私钥、token、本地环境值、生成垃圾或其他疑似误入文件。真实 `.env`、运行数据、日志和 `.migration-reports/` 不属于公开源码；发现疑似问题则停止。
5. 总结变更的主要目的及重要细节，据此选择提交类型：`feat` 表示新增功能或行为，`bugfix` 表示修复缺陷或回归，`chconf` 表示配置变更。
6. 混合变更按主导目的选择类型；没有合适类型或多个目的同等重要时，请用户选择或拆分提交，不另造类型。

### 原始字节与跨平台换行检查

- 变更涉及文件 SHA-256、字节长度、冻结文本夹具、知识 manifest，或 Windows 工作区向 Linux Docker/CI 提供输入时，检查 `git ls-files --eol`、`git check-attr` 和 `core.autocrlf`。检查范围包含实际加载的未修改依赖，不能只比对变更文件。
- 区分 HEAD/index 的 Git blob、工作区文件和镜像中的字节。Docker COPY 会保留工作区的 CRLF；`git status` 干净或工作区与镜像哈希一致，均不能证明与 Linux 检出一致。
- 使用只读 `git cat-file` 获取原始 blob；按原始字节比较，避免 PowerShell 文本管道重新编码。使用 archive 导出时显式控制本次命令的 `core.autocrlf`（例如 `git -c core.autocrlf=false archive`），并核对导出文件与目标 tree 的 blob；仍须考虑 `eol`、filter、export-subst 和 export-ignore 属性，不能假设 archive 必然原样输出。
- 正式验证应从实际拟提交内容构造独立、可追溯的 Git 快照，在 Docker 中运行，记录 tree、源码范围、镜像及报告。有未提交修改时不能只验证旧 HEAD；可用临时 index 构造候选 tree，但不得替换或污染用户真实 index，也不得混入无关文件。已有报告仅在相关源码、依赖和原始字节与候选快照一致时复用。
- 发现 LF/CRLF、字节长度或哈希差异时按真实验证故障停止，说明差异来源和当前暂存/提交状态。换行转换、添加属性、更新 golden/manifest 不属于允许自动修复的行尾空白；须由用户授权的修复任务处理，不能为了提交通过静默归一化、改写基线或修改全局 Git 配置。
- 复核最终工作区状态时，若普通 status 与实际 diff 不一致，可用 `git -c core.fsmonitor=false status --short --branch` 排除缓存影响；不能据一次空 status 忽略实际残留修改。

## 编写双语提交信息

每次提交必须同时包含标题（title/subject）和正文（body），不能省略任一语言。

标题严格使用以下单行格式：

```text
<type>: <英文描述> / <中文描述>
```

- `<type>` 只能是 `feat`、`bugfix` 或 `chconf`。
- 英文描述在前，简体中文描述在后，以一个空格、`/`、一个空格分隔；冒号后有一个空格。
- 两种描述表达相同的主要变更，简洁且能独立理解，不新增 scope、工单前缀、句末句号或其他类型。
- 用户仅提供一种语言时，补充语义一致的另一种语言，不用原文重复冒充翻译。

正文先写完整英文描述，空一行后再写完整简体中文描述。标题与正文之间也空一行。正文可使用段落或列表；使用列表时先写完英文列表，再空一行写中文列表，不逐条交错中英文。两种语言中的实现细节、动机、影响和验证结论须一致；代码标识、命令、路径、API、库及产品名可保持原样。

示例：

```text
feat: Improve shared library provider resolution / 改进动态库提供者解析

- Resolve providers from configured library paths
- Add actionable errors for missing providers

- 从已配置的库路径中解析提供者
- 为缺失的提供者提供可操作的错误信息
```

提交前检查标题顺序与分隔符、正文两种语言的完整性、英文正文和中文正文间的空行，以及语义是否一致。将完整信息写入 UTF-8 临时文件，再使用 `git commit -F <消息文件路径>`，避免多行 Shell 引号或字符转义破坏中文、换行或触发命令替换。临时消息文件不纳入提交。

## 验证、提交与推送

1. 按仓库规则及变更范围执行验证。编译、测试、覆盖率、依赖安装和代码生成均在 Docker 中完成，按模块顺序执行并限制资源，使用独立容器、网络和数据卷。入口见根目录 `docs/开发指南.md` 及各模块说明。
2. 代码变更须验证单元测试和整体及受影响模块的行覆盖率、可用分支覆盖率至少 90%，纳入未被加载的自有可执行源码，并列明合理排除项。遵守仓库当前前端覆盖率例外及其他更严格规则；不能用构建或集成测试替代单元测试。需完整交付验证时，从根目录执行 Compose 构建并一次性 `docker compose up -d --wait`，检查健康状态、日志和代表性流程。纯文档变更检查内容、链接和格式，覆盖率不适用。
3. 仅暂存计划提交的路径，检查完整暂存 diff，确认非空且与总结一致；至少执行 `git diff --cached --check`。限定的空白问题按上述规则修复后重新检查。验证失败或必需验证受阻时停止，不能宣称验收完成。
4. 使用双语标题和必需的双语正文创建提交，让 hook 正常运行；除非用户明确要求，不使用 `--no-verify`。
5. 推送前再次 fetch 拉取校验远程与推送远程（相同时只需一次），与先前记录比较。任一对应分支前进、删除或发生其他变化时停止，保留本地提交并等待用户决定，不自动整合远程变更或强推。
6. 推送到已确定的推送远程和同名目标分支。仅在当前分支没有 tracking 配置时按需设置 upstream tracking；已有 tracking 配置时保留它，使用显式远程和分支推送。
7. 验证最终状态，报告提交哈希、完整双语标题、拉取校验来源、推送目的地、实际执行的检查和未执行项，以及剩余工作区变更。代码验证同时报告覆盖率范围、行/分支结果和报告位置；不可用指标如实标注。

没有可提交内容时，不创建空提交，说明工作流已停止。提交成功后 fetch 或 push 失败时，保留本地提交，报告具体错误和当前状态，等待用户决定恢复方式。
